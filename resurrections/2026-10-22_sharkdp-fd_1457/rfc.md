# RFC: New .git Handling has no opt out

Summary
---
Add a new CLI flag `--git-ignore-opt-out` to fd that disables the default automatic exclusion of the top‑level `.git` directory while preserving all other VCS ignore handling (e.g., `.hg`, `.svn`). The flag is mutually exclusive with `--no-ignore-vcs` and integrates cleanly with the existing ignore crate configuration.

Motivation
---
The current implementation of fd unconditionally skips any directory named `.git` during a search. This behaviour was introduced to avoid traversing massive Git object stores, but it also prevents users from intentionally searching inside a repository's `.git` directory (for example, to locate hooks, configuration, or corrupted objects). The upstream issue reports that many power‑users want a simple opt‑out rather than a full removal of VCS ignore handling. Since ignore‑crate 0.5 now exposes `WalkBuilder::git_ignore(bool)` and Rust 1.70 provides stable `std::fs::read_dir` semantics, implementing a fine‑grained toggle is low‑risk. Providing an explicit flag improves ergonomics, aligns fd with other tools (e.g., ripgrep's `--no-ignore` family), and reduces the need for work‑arounds such as `--no-ignore-vcs` which also disables other VCS ignores.

Detailed Design
---
1. **CLI changes**: Extend the Clap v4 definition in `src/args.rs` with a new boolean flag:
   ```rust
   #[arg(long = "git-ignore-opt-out", conflicts_with = "no-ignore-vcs", help = "Do not automatically ignore .git directories; other VCS ignores remain active")] 
   pub git_ignore_opt_out: bool,
   ```
   The flag is placed in the same mutually exclusive group as `--no-ignore-vcs`.
2. **Configuration struct**: Add `git_ignore_opt_out: bool` to the central `Config` struct and propagate it from argument parsing.
3. **WalkBuilder integration**:
   ```rust
   let mut builder = WalkBuilder::new(&config.path);
   // Existing settings …
   if config.git_ignore_opt_out {
       builder.git_ignore(false); // disables the built‑in .git filter
   } else {
       builder.git_ignore(true); // default behaviour
   }
   // Preserve other VCS ignores
   if config.ignore_vcs {
       builder.vcs_ignore(true);
   }
   ```
   The `ignore` crate already respects `.gitignore` files; we only toggle the automatic directory filter.
4. **FilterBuilder fallback**: For older ignore‑crate versions (should never be compiled in CI) we add a conditional compilation guard that manually adds a `FilterBuilder` rule to exclude `.git` when the flag is *not* set, mirroring the previous behaviour.
5. **Search execution path**: Pass the flag through `SearchContext` so that parallel workers share the same setting. No changes to the core matching logic are required.
6. **Documentation & tests**:
   - Update `man/fd.1`, README and help output to describe the flag.
   - Add unit tests in `tests/cli.rs` covering:
     * default behaviour (`.git` skipped)
     * `--git-ignore-opt-out` (`.git` traversed, other VCS ignored)
     * interaction with `--no-ignore-vcs` (mutual exclusivity enforced by Clap)
   - Add integration test that searches inside a synthetic repo containing a file inside `.git/objects` and asserts it is found only when the flag is present.

Drawbacks
---
* **Increased surface area**: Introducing another flag adds complexity to the CLI and may confuse users who are unaware of the subtle difference between `--no-ignore-vcs` and `--git-ignore-opt-out`.
* **Potential performance impact**: Traversing `.git` can be expensive for large repositories; users may inadvertently enable the flag and experience slower searches.
* **Maintenance burden**: Future changes to the ignore crate's API will need to keep this conditional logic in sync.

Alternatives
---
1. **Remove the automatic `.git` filter entirely** and rely on `--no-ignore-vcs` for users who want it. This would break existing expectations for the majority of users and could cause regressions in scripts that assume `.git` is ignored.
2. **Expose a generic `--ignore-dir <PATTERN>` flag** allowing users to specify any directory to exclude. While flexible, it would not address the specific need for an easy opt‑out and would require parsing and pattern matching logic.
3. **Add an environment variable** (e.g., `FD_GIT_IGNORE=0`). This is less discoverable than a CLI flag and would complicate documentation.

Unresolved Questions
---
* Should the flag also affect hidden‑directory handling (`--hidden`)? Current design keeps them independent, but some users may expect a unified "search everything" mode.
* Do we need to emit a warning when the flag is used on a repository larger than a configurable threshold (e.g., >500 MiB) to alert users about possible performance degradation?
* How will this interact with the upcoming `--threads=0` auto‑scaling feature? No functional conflict is expected, but testing on highly parallel runs is required.
