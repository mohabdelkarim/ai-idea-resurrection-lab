# RFC: rate()/increase() extrapolation considered harmful

Summary
Prometheus will replace the built‑in rate() and increase() extrapolation logic with a configurable linear estimator. The change introduces an Extrapolator interface, a default LinearExtrapolator implementation, and a plugin registration point. Operators can enable the new estimator via a command‑line flag (e.g., --extrapolation=linear) and tune the regression window with --extrapolation.window. Legacy behavior remains the default for backward compatibility, ensuring existing dashboards continue to work while offering more accurate, statistically‑grounded estimates for dashboards that opt‑in.

Motivation
The current extrapolation algorithm in rate() and increase() assumes a constant value between the first and last sample of the range vector, then scales the observed delta to the full interval. This approach can produce significant error when the underlying series is noisy, has irregular scrape intervals, or experiences rapid changes near the edges of the window. Users have reported misleading spikes in Grafana panels and inaccurate alert thresholds. Since Prometheus 2.40 the engine supports subqueries and richer range‑vector semantics, and the OpenMetrics spec now defines explicit reset handling, removing the historical ambiguity that prevented a more sophisticated estimator. A linear regression‑based estimator can dramatically reduce bias, provide confidence intervals, and be computed efficiently using the new per‑sample interpolation primitives introduced in the TSDB.

Detailed Design
1. Extrapolator Interface
   ```go
   type Extrapolator interface {
       EstimateRate(samples []sample, window time.Duration) (float64, error)
       EstimateIncrease(samples []sample, window time.Duration) (float64, error)
   }
   ```
2. LinearExtrapolator
   - Reads raw samples from the block reader for the requested range.
   - Applies weighted least‑squares regression where weights decay with age (configurable decay factor).
   - Returns the slope as the rate and integrates the slope over the window for increase.
   - Computes a 95% confidence interval and attaches it to the result as a hidden label (e.g., __ci_low, __ci_high).
3. Engine Integration
   - QueryEngine gains an optional Extrapolator field. If nil, it falls back to the legacy extrapolation.
   - The parser adds a new optional modifier to rate()/increase(): rate(v[5m] extrapolate="linear")
   - Command‑line flags: --extrapolation=legacy|linear, --extrapolation.window=5m, --extrapolation.decay=0.9
4. Plugin System
   - Extrapolators can be registered at init via `prometheus.RegisterExtrapolator(name string, impl Extrapolator)`.
   - Future strategies (spline, Bayesian) can be added without core changes.
5. Testing & Benchmarks
   - Unit tests cover reset detection, missing samples, and confidence interval correctness.
   - Benchmark suite compares legacy vs linear on synthetic workloads (high jitter, variable scrape intervals).
6. Documentation & Migration
   - Updated PromQL reference page with new syntax.
   - Grafana panel docs showing how to enable confidence‑interval rendering.
   - Migration guide recommending gradual rollout via feature flag.

Drawbacks
- Additional CPU overhead: linear regression per range vector adds ~15‑20% CPU at typical query loads, though caching of regression coefficients mitigates the impact.
- Increased memory usage: raw sample slices must be retained longer than before, raising per‑query memory by ~5 MiB in worst‑case dashboards.
- Potential backward‑compatibility surprises if users unintentionally enable the new estimator, leading to different alert firing patterns.

Alternatives
1. Keep the legacy extrapolation and provide a separate function (e.g., linear_rate()) that users can call explicitly. This avoids altering existing functions but duplicates API surface.
2. Implement a simple moving‑average smoothing before the legacy extrapolation. This reduces jitter but does not address the fundamental bias of constant‑value extrapolation.
3. Offload extrapolation to the visualization layer (Grafana) using client‑side regression. This shifts load to the UI and cannot be used for alerting.

Unresolved Questions
- What is the optimal default regression window for most workloads? We propose 5 minutes, but a per‑metric heuristic may be needed.
- How should confidence intervals be exposed to alerting rules? Should there be a separate function (rate_ci) or a label convention?
- Will the plugin registration mechanism interfere with existing Prometheus extensions that already use init hooks?
- How to handle extreme outliers in the regression without breaking the estimator? A robust regression option is being considered for future releases.
