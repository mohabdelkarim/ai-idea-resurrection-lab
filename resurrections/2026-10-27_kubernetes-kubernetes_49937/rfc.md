# RFC: Support httpHead for pod livenessProbe

Summary
-------
Add support for the HTTP HEAD method in the pod livenessProbe configuration. The change introduces an optional `httpMethod` field on the existing `HTTPGetAction` struct, defaulting to `GET` for backward compatibility. When `httpMethod: "HEAD"` is specified, the kubelet will issue an HTTP HEAD request to the target container endpoint and evaluate the response code and headers according to the existing liveness semantics. This RFC outlines the motivation, design, trade‑offs, alternatives, and open questions for the feature.

Motivation
----------
Many applications expose health endpoints that are safe to query with HEAD – they return the same status code as GET but omit the response body, reducing network overhead and CPU usage. Current Kubernetes probes only support GET, POST (via exec) or TCP, forcing users to either accept the extra payload or implement custom scripts. Adding HEAD improves efficiency for high‑scale workloads, aligns Kubernetes with the HTTP spec that encourages HEAD for lightweight checks, and leverages the extensible ProbeHandler API introduced in v1.24. The change is non‑breaking because the new field is optional and defaults to GET, preserving existing behavior.

Detailed Design
---------------
1. **API changes**
   - Extend `core/v1.HTTPGetAction` with `httpMethod?: string` (enum: "GET", "HEAD").
   - Update OpenAPI schema, client-go generated code, and protobuf definitions.
   - Validation webhook: reject any value other than GET or HEAD for liveness/readiness probes; allow future extensions for other verbs in custom ProbeHandlers.
2. **Kubelet executor**
   - In `probe/http.go`, construct the request via `http.NewRequest(action.HTTPMethod, url, nil)`; for GET the existing logic remains unchanged.
   - Ensure the request body is nil for HEAD and that the response body is discarded without reading.
3. **Testing**
   - Unit tests for the executor covering both GET and HEAD paths, including status code handling and timeout behavior.
   - E2E tests: deploy a pod with a simple HTTP server that returns 200 for HEAD and 200 for GET; verify that the pod becomes Ready/Live as expected.
4. **Documentation**
   - Update the pod spec reference page, examples, and `kubectl explain pod.spec.containers.livenessProbe.httpGet.httpMethod`.
   - Add a note about when to prefer HEAD.
5. **Backward compatibility**
   - Existing manifests without `httpMethod` continue to behave exactly as before.
   - No version skew impact because the field is ignored by older apiservers/kubelets that do not recognize it.

Drawbacks
---------
* **Increased surface area**: Adding a new field requires validation updates and may introduce bugs if the field is mis‑typed.
* **Runtime support variance**: Some older container runtimes may not expose HEAD semantics correctly, though the kubelet performs the request directly, mitigating most issues.
* **Security considerations**: HEAD can be used to probe headers; we must ensure that existing security policies (NetworkPolicies, PodSecurityPolicies) treat HEAD like GET, which they already do for HTTP traffic.

Alternatives
-----------
1. **Use exec probe**: Users could run `curl -I` via an exec probe. This adds container overhead and duplicates logic already present in the HTTPGet path.
2. **Custom ProbeHandler**: Implement a full custom handler plugin to issue HEAD. This is more complex and unnecessary for the simple case of adding a verb.
3. **No change**: Keep only GET, accepting the minor inefficiency. This would leave the problem unsolved for workloads that would benefit.

Unresolved Questions
--------------------
* Should we allow other safe methods (OPTIONS, TRACE) in the future, and how would validation evolve?
* How will admission controllers that enforce specific probe configurations handle the new field?
* Are there any edge‑cases with HTTP/2 or HTTP/3 where HEAD handling differs and requires additional testing?
* Should we expose a metric `probe_http_method_total` to track usage of GET vs HEAD for observability?
