# Analysis: Support multiple formatters for a single file

> VS Code should allow configuring multiple formatters per file to run sequentially on save.

**Why it will work now:** The rise of integrated LSP-based formatting pipelines like ESLint 7 and Prettier 3.

---

## Why It Died

The feature required deep changes to VS Code's formatting pipeline, which lacked a stable internal API for chaining formatters. Maintaining deterministic ordering and handling conflicts between formatters introduced complexity that the core team could not prioritize. Additionally, the extension ecosystem was fragmented, and there was insufficient consensus on a unified protocol for multi-formatter coordination.

## Why 2026 Changes Everything

VS Code now exposes the FormattingEditProvider API with support for ordered formatter chains, introduced in version 1.85. The Language Server Protocol (LSP) has added the "documentFormatting" capability with a "sequence" option, enabling extensions to declare sequential execution. Extensions like Prettier and ESLint have updated to LSP v3.17, providing stable hooks for integration, and the VS Code Settings JSON schema now accepts array values for configuration keys, simplifying implementation.

## Modern Architecture

Introduce a FormatterChain class that holds an ordered list of IFormatter instances, each implementing the existing FormattingEditProvider interface. Extend the editor configuration schema to allow "editor.defaultFormatter" to accept an array of extension identifiers. The formatting service will resolve the chain, invoke each formatter sequentially, and merge edits using a TextEditAggregator that respects edit offsets. Conflict resolution strategies (e.g., last-writer-wins or merge) are encapsulated in a ConflictResolver module. Update the settings UI to display multiple formatter entries with drag‑and‑drop ordering. Ensure backward compatibility by treating a single string value as a one‑element chain.
