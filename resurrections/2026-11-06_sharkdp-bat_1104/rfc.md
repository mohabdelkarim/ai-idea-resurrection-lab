# RFC: Default theme compatible with light/dark terminals

1. Summary
Add a dynamic default theme to bat that automatically adapts to the terminal's background (light or dark). The feature introduces a ThemeManager component, a new `dynamic_theme` flag in the configuration, and uses cross‑platform background detection via OSC 11 (crossterm) and fallback heuristics. When enabled, bat selects the appropriate palette at runtime, providing optimal contrast without user intervention.

2. Motivation
bat ships with a static default theme that assumes a dark background. Users on light‑themed terminals experience washed‑out syntax highlighting, while dark‑themed users may see overly bright colors if they manually switch to a light palette. Historically bat could not reliably detect the terminal background because terminfo lacks such data. Since 2024, major terminal emulators (e.g., Kitty, Alacritty, iTerm2, Windows Terminal) implement OSC 11 queries, and the Rust ecosystem now offers `crossterm` and `termcolor` APIs to retrieve the background color. Providing an adaptive default improves out‑of‑the‑box usability, aligns bat with modern UI expectations, and reduces the need for users to maintain custom config files for each environment.

3. Detailed Design
* **Theme Struct**: Define `struct Theme { foreground: Color, background: Color, syntax: HashMap<SyntaxKind, Color> }`. Two built‑in theme files (`light.toml`, `dark.toml`) reside in `assets/themes/`.
* **ThemeManager**: New module `theme_manager.rs` exposing `fn detect_background() -> Result<BackgroundKind, Error>` which attempts:
  1. OSC 11 query via `crossterm::style::Color::query_background()`.
  2. Fallback to `COLORTERM` and known terminal defaults.
  3. If detection fails, default to `BackgroundKind::Dark`.
* **Config Extension**: Add `dynamic_theme: bool` (default `true`) and `fallback_theme: String` (default `dark`). Config parsing updates automatically.
* **Runtime Selection**: At program start, if `dynamic_theme` is true, ThemeManager selects `light` or `dark` theme based on detection and loads the corresponding TOML file into a global `Theme` instance.
* **Rendering Pipeline**: Modify `printer.rs` to accept a `&Theme` reference. Syntax highlighter (`syntect`) receives the palette mappings, ensuring colors are applied consistently.
* **Performance**: Background detection runs once per process; the OSC 11 query is non‑blocking and cached. The added overhead is <1 ms on typical terminals, negligible compared to file I/O and syntax parsing.
* **Testing**: Add unit tests mocking `crossterm` responses for light, dark, and error cases. Integration tests spawn a pseudo‑terminal with a preset background and verify that the generated ANSI escape sequences match the expected palette.
* **Documentation**: Update `README.md` and `man/bat.1` with a new section describing `--dynamic-theme` and the environment variables used for fallback.

4. Drawbacks
* **Dependency Footprint**: Introducing `crossterm` adds ~200 KB to the binary and pulls in additional transitive crates, slightly increasing compile time.
* **Reliability**: Not all terminals implement OSC 11; in those cases the fallback may misclassify the background, leading to sub‑optimal contrast.
* **Complexity**: The rendering path now depends on runtime state, which could complicate future refactors of the highlighting engine.

5. Alternatives
* **User‑Only Config**: Keep the current static theme and require users to set `--theme=light` manually. Simpler but places burden on users.
* **Environment Variable**: Introduce `BAT_THEME=auto` that forces detection without a full manager component. This reduces code but still needs detection logic.
* **Compile‑Time Feature Flag**: Provide an optional `dynamic-theme` Cargo feature that users can enable. This avoids default binary bloat but requires downstream rebuilds.

6. Unresolved Questions
* How should bat behave when the terminal background changes mid‑session (e.g., user toggles dark mode)? Should we poll periodically or expose a signal‑based refresh?
* What is the best heuristic for terminals that return an RGB value close to the midpoint (e.g., #808080)? Should we prefer dark for ambiguous cases?
* Should we allow users to supply custom light/dark theme files via a config directory, and how would discovery interact with the built‑in assets?
* Is there a need for a third "high‑contrast" palette for users with accessibility requirements?
