# RFC: Markdown Preview - Navigate back

Summary
Add back‑navigation support to the built‑in Markdown preview in VS Code. A new command `markdown.preview.navigateBack` will allow users to return to the previously viewed preview page using standard navigation shortcuts (Backspace, Mouse4) when the preview panel has focus. The implementation relies on the enhanced Webview API introduced in VS Code 1.85, a `PreviewNavigationManager` that tracks a per‑preview URI stack, and integration with the workbench navigation service.

Motivation
The current Markdown preview treats every link click as a one‑way navigation: the previous page is discarded and the built‑in editor back button does not affect the preview. Users who browse documentation, tutorials, or multi‑page notes inside the preview frequently lose their place and must reopen earlier sections manually. The lack of a stable API to intercept link clicks previously prevented a clean solution. With the new bidirectional messaging and navigation history service, we can now expose a preview‑specific back stack without compromising performance or editor history. Providing this feature aligns VS Code with typical web‑browser behavior, improves accessibility (keyboard‑only navigation), and reduces friction for power users.

Detailed Design
1. **PreviewNavigationManager** (src/markdown/previewNavigationManager.ts)
   - Maintains a `Stack<Uri>` per preview webview instance.
   - Exposes `push(uri)`, `pop(): Uri | undefined`, and `peek(): Uri | undefined`.
   - Persists the stack in the webview state (`vscode.setState`) to survive reloads.
2. **Webview Extension**
   - Update `markdownPreview.ts` to listen for `click` events on anchor tags via `window.addEventListener('click', ...)`.
   - On link activation, prevent default, send a message `{ type: 'linkClick', target: href }` to the extension host.
   - Host receives the message, calls `navigationManager.push(targetUri)`, then updates the webview source (`panel.webview.html = render(targetUri)`).
3. **Command Registration**
   - Register `markdown.preview.navigateBack` in `package.json` with `when: 'markdownPreviewFocus'`.
   - Command implementation calls `navigationManager.pop()`; if a URI is returned, the webview is refreshed to that URI.
4. **Workbench Integration**
   - Contribute to `navigation` contribution point to map Backspace and Mouse4 to `markdown.preview.navigateBack` when the preview is active.
   - Ensure the command does not interfere with the global editor navigation stack by checking `vscode.window.activeTextEditor` context.
5. **Testing**
   - Unit tests for `PreviewNavigationManager` covering push/pop edge cases.
   - Integration test that simulates link clicks and verifies the back command restores the previous page.
6. **Documentation**
   - Update `README.md` of the Markdown extension with usage examples and keybinding information.

Drawbacks
- Introduces a per‑preview navigation stack, increasing memory usage marginally (a few URIs per open preview). 
- Adds complexity to the preview webview code, which could affect load times if not optimized; however, the impact is expected to be negligible (<5 ms per navigation).
- Potential for confusion if users expect the editor back button to affect the preview; mitigated by clear UI cues and context‑aware keybindings.

Alternatives
1. **Reuse Global Navigation History** – Hook the preview into the existing editor history service. This would blur the distinction between editor and preview navigation and could cause unexpected side effects when switching panes.
2. **Open Links in New Preview Tabs** – Instead of a back stack, always open links in a new preview panel. This avoids a stack but quickly leads to tab proliferation and a poorer UX.
3. **External Browser** – Direct all links to the external browser, eliminating in‑preview navigation entirely. This sacrifices the integrated reading experience that many users rely on.
Each alternative either compromises UX or adds more overhead than the proposed stack‑based approach.

Unresolved Questions
- Should the navigation stack be limited (e.g., max 50 entries) to bound memory usage? Preliminary tests suggest 50 is safe, but we need to confirm with telemetry.
- How should the stack behave when the preview is refreshed (e.g., due to theme change) – should it be cleared or preserved? Current design preserves it via `setState`, but edge cases need validation.
- Do we need a UI indicator (breadcrumb or history dropdown) to show the stack depth, or is the command‑only approach sufficient? A lightweight tooltip could be added later based on user feedback.
