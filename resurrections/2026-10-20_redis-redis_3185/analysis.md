# Analysis: Replace "master" and "slave" terms in Redis

**Why it will work now:** The introduction of Redis 6's ACL and module system enables safe deprecation of master/slave terminology.

## Why It Died

The proposal required extensive renaming of commands, configuration options, and documentation, which risked breaking backward compatibility for many deployments. Redis maintainers lacked consensus on appropriate replacement terms, leading to indecision. Community bandwidth was limited as core development focused on performance and new features rather than terminology changes.

## Why 2026 Changes Everything

Redis 6 introduced a robust ACL system and a stable module API, allowing deprecation warnings and aliasing of old command names. The Redis Module SDK now supports seamless command renaming without downtime. Additionally, the widespread adoption of CI pipelines makes large‑scale refactoring safer and more testable than in 2016.

## Modern Architecture

Implement a compatibility layer that maps legacy "master" and "slave" commands to their new equivalents using RedisModule_CreateCommand aliases. Introduce configuration flags (e.g., "rename-legacy-terms") that toggle the aliasing behavior at startup. Update the internal replication state machine to use neutral enum values like REPLICA_ROLE and PRIMARY_ROLE. Provide deprecation warnings via the server log and the ACL system when legacy terms are used. Ensure all documentation generators reference the new terminology, and add automated tests that verify both old and new command paths function correctly.
