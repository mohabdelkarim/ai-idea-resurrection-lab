# RFC: Tainted `null_resource` with `destroy provisioner` does not run the destroy command.

1. Summary
This RFC proposes to modify the Terraform core null_resource implementation so that a tainted null_resource triggers its destroy provisioner during the subsequent apply. The change introduces a taint‑aware lifecycle flag, updates the provisioner executor to schedule destroy actions when a resource transitions from tainted to healthy, and adds comprehensive unit tests. The behavior will be enabled for Terraform 0.12+ configurations while preserving legacy semantics for older versions.

2. Motivation
The current Terraform engine treats a taint as a simple state flag that forces recreation, but it does not differentiate the recreation path from a normal destroy‑and‑create sequence. As a result, destroy provisioners attached to a null_resource are silently skipped when the resource is tainted and then re‑applied. This violates user expectations: a destroy provisioner is meant to clean up external artifacts (files, containers, cloud resources) before the resource is recreated. Skipping it can leave orphaned assets, cause cost leakage, and break idempotent workflows. Since Terraform 0.12 introduced a clearer provisioner lifecycle model and the SDK now supports fine‑grained diff inspection, we have the technical foundation to correctly handle this edge case without regressions.

3. Detailed Design
- **ResourceDiff Extension**: Add a boolean field `TaintReplacement` to `ResourceDiff`. When the diff is generated, if the prior state is tainted, this flag is set.
- **Apply Phase Hook**: In the core apply loop, detect `TaintReplacement`. If true, invoke the destroy provisioner runner before the normal create provisioner runner.
- **Provisioner Executor Changes**: The executor will receive a context indicating `DestroyPhase`. It will load provisioner configurations marked with `when = "destroy"` and execute them. Existing destroy provisioners continue to run on explicit `terraform destroy`.
- **Null Resource Provider Update**: Modify `null_resource`'s `Apply` method to check the diff flag and call `resourceProvisionerRun(destroyContext)` when appropriate.
- **Version Gating**: The new path is activated only when the configuration's required_version constraint includes 0.12 or later. For older configurations, the legacy path (skip destroy on taint) is retained to avoid breaking existing pipelines.
- **Testing**: Add unit tests using `terraform-plugin-sdk/v2/helper/resource`. Tests will:
  1. Create a null_resource with both create and destroy provisioners.
  2. Taint the resource via `terraform taint`.
  3. Run `terraform apply` and assert that the destroy provisioner was executed (captured via a temporary file or log).
  4. Verify that the create provisioner runs afterwards.
- **Documentation**: Update the null_resource and provisioner docs to describe the new taint‑driven destroy behavior and the version gating.

4. Drawbacks
- **Complexity Increase**: Introducing a new diff flag and conditional execution path adds code complexity to the core apply loop, which may affect maintainability.
- **Performance Overhead**: For every tainted resource the engine now performs an extra provisioner run, potentially increasing apply time in large infrastructures with many null_resources.
- **Backward Compatibility Risks**: Although gated, there is a small risk that some legacy configurations inadvertently meet the version check and experience changed behavior.

5. Alternatives
- **User‑Side Workaround**: Recommend users manually run `terraform destroy -target=null_resource.example` before re‑applying. This avoids core changes but places the burden on users and is error‑prone.
- **Deprecate Destroy Provisioners on null_resource**: Remove support for destroy provisioners entirely, encouraging users to migrate to explicit resources. This would simplify the codebase but break existing workflows that rely on destroy actions.
- **Separate CLI Flag**: Introduce a `-run-destroy-on-taint` flag to opt‑in to the behavior. This reduces automatic changes but adds a new user‑visible option and complicates CLI ergonomics.

6. Unresolved Questions
- How should the engine handle multiple taint cycles on the same resource within a single plan? Should destroy provisioners run once per taint or once per apply?
- Should we expose a configuration attribute (e.g., `lifecycle { allow_destroy_on_taint = true }`) to let users explicitly enable or disable the behavior per resource?
- Are there any side‑effects on provider‑implemented resources that also rely on the `ResourceDiff` structure? A compatibility matrix will be needed.
- What is the best mechanism to capture destroy provisioner execution in tests without relying on filesystem side effects?
