# RFC: kubectl run from a manifest file

1. Summary
Add a new optional flag `--from-file` to `kubectl run` that allows users to supply a pod manifest (YAML or JSON). When the flag is present, `kubectl run` will load the manifest, apply any command‑line overrides (e.g., --image, --env, --port), and then create the object using server‑side apply. The existing `kubectl run` behaviour remains unchanged when the flag is omitted, preserving backward compatibility.

2. Motivation
The current `kubectl run` command only creates a pod from a minimal set of flags. Users who need a reproducible pod definition must first write a full manifest and then invoke `kubectl create -f`. This two‑step workflow is error‑prone and defeats the purpose of the convenience command. Since client‑go 0.26 now offers a stable server‑side apply API and the cobra framework supports dynamic flag generation, we can safely merge a base manifest with overrides at runtime. Providing a single command that both loads a manifest and allows selective overrides reduces friction for developers, CI pipelines, and ad‑hoc debugging sessions.

3. Detailed Design
* **Command Extension**: Extend the `kubectl run` cobra command with a new `--from-file` (string) flag. The flag value is a path to a local file or a URL (http/https). Validation ensures the file exists and is parsable as a Kubernetes object.
* **RunFromManifest Struct**: Implement a new struct `RunFromManifest` that satisfies the existing `RunOptions` interface. It holds fields for the loaded `unstructured.Unstructured` object, a map of overrides, and a reference to the generic `Factory`.
* **Manifest Loading**: Use `k8s.io/apimachinery/pkg/util/yaml` to decode the file into an `unstructured.Unstructured`. If the object kind is not Pod, return an error (future extensions may support Deployments).
* **Override Merging**: Parse standard `kubectl run` flags (`--image`, `--env`, `--port`, `--replicas`, etc.) into a map. Apply these overrides onto the loaded object using the server‑side apply patch format. For example, an `--image` flag will set `spec.containers[0].image`.
* **Template Rendering**: Before applying, run the manifest through Go's `text/template` engine with a predefined data struct exposing `{{ .ImageTag }}`. This enables inline substitution of image tags without manual string manipulation.
* **Server‑Side Apply**: Call `client-go`'s `ApplyPatch` method with `fieldManager="kubectl-run"` and `force=true`. This preserves existing secret references and other immutable fields while updating only the overridden sections.
* **Error Handling**: Provide clear error messages for missing required fields, unsupported kinds, and merge conflicts. Exit codes follow existing `kubectl run` conventions.
* **Testing**: Add unit tests covering: loading a valid manifest, applying overrides, handling unknown flags, and server‑side apply failures. Integration tests will run against a kind cluster to verify end‑to‑end behavior.
* **Documentation**: Update the `kubectl run` man page and online docs with a new section showing examples:
  ```
  kubectl run myapp --from-file=pod.yaml --image=repo/app:v2 --env=DEBUG=true
  ```

4. Drawbacks
* **Complexity Increase**: The `run` command now contains two code paths (manifest‑based and flag‑only). Maintaining parity between them may increase maintenance burden.
* **Potential for Confusion**: Users might expect all manifest fields to be mergeable; unsupported fields will be silently ignored unless explicitly validated, leading to surprising results.
* **Performance Overhead**: Loading and templating a file adds I/O and CPU cost, though negligible for typical use cases.

5. Alternatives
* **Separate Sub‑command**: Introduce `kubectl run-from-file` instead of overloading `run`. This would keep the original command simple but would fragment the user experience.
* **Leverage `kubectl create -f` with `--dry-run=client`**: Users could generate a manifest via `run`, edit it, then apply. This requires extra steps and does not provide inline overrides.
* **Extend `kubectl apply -f` with a `--set` flag**: Similar to Helm, but would require a larger redesign of `apply` and is outside the scope of `run`.

6. Unresolved Questions
* Should we support other workload kinds (Deployment, Job) via the same flag, or limit to Pod for the initial release?
* How should we handle multiple containers in the manifest when the user supplies only a single `--image` flag? Should we target the first container or require an explicit `--container-name` flag?
* What is the best strategy for template variable scoping to avoid security issues when rendering user‑provided files?
* Do we need to add a `--dry-run=server` mode for this path to allow previewing the merged manifest before actual creation?
