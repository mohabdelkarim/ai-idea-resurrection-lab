# RFC: feat: collections/docs for modelfiles with models

1. Summary
Add a native Retrieval‑Augmented Generation (RAG) configuration to the existing ModelFile schema in Open‑WebUI. The extension introduces an optional `ragConfig` object that specifies a target vector store and a list of document source URIs. A new `RagService` layer will translate this configuration into LangChain 0.2 loader calls, generate embeddings, and populate the selected vector store (Pinecone, Qdrant, or local FAISS). Model creation and update endpoints are extended to accept and validate `ragConfig`. The UI gains a "Documents" tab in the model wizard for uploading or linking files. This RFC details the design, implementation steps, and integration points.

2. Motivation
Open‑WebUI currently treats model definitions as pure inference artifacts. Users who need RAG must manually create vector stores and manage document ingestion, which fragments the workflow and raises the barrier to entry. Since LangChain 0.2 now offers a unified document loader API and OpenAI's newer GPT models accept a `vector_store` field, we can automate the entire ingestion pipeline. Providing first‑class RAG support will:
- Reduce friction for developers building knowledge‑base chat assistants.
- Align Open‑WebUI with emerging standards in the LLM ecosystem.
- Enable seamless switching between hosted vector‑store services via dependency injection.
- Strengthen the product offering, making it more competitive for enterprise deployments.

3. Detailed Design
**Schema Extension**
```json
ModelFile {
  id: string,
  name: string,
  provider: string,
  model: string,
  ...,
  ragConfig?: {
    vectorStore: "pinecone" | "qdrant" | "faiss",
    storeConfig: object, // provider‑specific connection details
    documents: [
      { uri: string, type: "url" | "file", meta?: object }
    ]
  }
}
```
**RagService**
- Injected with a `VectorStoreFactory` that returns an implementation of a common `VectorStore` interface.
- `ingest(ragConfig)` iterates over `documents`, uses LangChain loaders (`WebBaseLoader`, `FileLoader`, etc.) to stream content, creates embeddings via the model's embedding endpoint, and upserts them into the store.
- Returns a status object and the store identifier for later retrieval.
**Controller Changes**
- `POST /api/v1/modelfiles` and `PUT /api/v1/modelfiles/:id` accept `ragConfig`.
- Validation against a JSON Schema ensures required fields per store type.
- After persisting the ModelFile, the controller calls `RagService.ingest` asynchronously; a webhook updates the ModelFile with ingestion status.
**Dependency Injection**
- `VectorStoreFactory` reads a global config (`VECTOR_STORE_DEFAULT`) and creates concrete classes: `PineconeStore`, `QdrantStore`, `FaissStore`.
- Allows future addition of services without code changes.
**UI Updates**
- Model creation wizard gains a "Documents" tab.
- Users can drag‑and‑drop files or add URLs; the UI builds the `ragConfig` JSON payload.
- Progress bar shows ingestion status via polling the ModelFile endpoint.
**Testing & Documentation**
- Unit tests for `RagService`, each `VectorStore` implementation, and controller validation.
- Integration tests simulate full ingestion flow with a mock LangChain loader.
- OpenAPI spec updated to include `ragConfig` schema.

4. Drawbacks
- Introduces additional latency during model creation as document ingestion may be time‑consuming.
- Increases surface area for misconfiguration (e.g., invalid store credentials) leading to failed model setups.
- Adds runtime dependencies on LangChain and vector‑store SDKs, increasing bundle size.
- Requires careful handling of large file uploads to avoid OOM errors; may need streaming support.

5. Alternatives
- **External RAG Service**: Keep model files unchanged and provide a separate microservice that users call after model creation. This decouples ingestion but adds operational complexity.
- **Manual Ingestion Only**: Document that users must manually populate vector stores. Simpler to implement but defeats the purpose of a seamless UI experience.
- **Limited Store Support**: Support only a single vector store (e.g., Pinecone) to reduce code paths. This would simplify the implementation but limit flexibility for self‑hosted deployments.

6. Unresolved Questions
- How should we handle document versioning when a user updates the `documents` list? Should we purge old embeddings or append?
- What quota or size limits should be enforced for uploaded files to protect the backend?
- Should ingestion be synchronous (blocking the POST response) for small payloads, or always async with a webhook?
- How will authentication/authorization be propagated to third‑party vector‑store SDKs in multi‑tenant deployments?
- Are there any licensing concerns with bundling LangChain 0.2 in the Open‑WebUI distribution?
