# RFC: add `--build-arg` for `docker compose up --build`

1. Summary
Docker Compose will gain a new flag `--build-arg` on the `docker compose up --build` command. This flag allows users to pass arbitrary build arguments directly to the image build step invoked by `up`. The implementation leverages the recent Cobra flag inheritance improvements and the Docker SDK's native build-arg support. The change is backward‑compatible, adds minimal surface area, and provides a more ergonomic workflow for developers who need to tweak image builds without editing the compose file.

2. Motivation
Historically, Compose required users to modify the `build:` section of a compose file or invoke a separate `docker compose build` command to supply build arguments. This extra step fragmented the developer experience and made CI pipelines more verbose. With Docker Engine 24.0's unified flag propagation and the refactored Compose CLI, the technical obstacles that prevented this feature have been removed. Providing `--build-arg` directly on `up --build` aligns Compose with the expectations set by `docker build --build-arg` and reduces friction for teams that generate images on‑the‑fly during compose deployments.

3. Detailed Design
* **CLI definition**: Extend the Cobra command for `up` in `cmd/up.go` to include `Flags().StringArrayVar(&opts.BuildArgs, "build-arg", []string{}, "Set build-time variables")`. The flag mirrors the existing `docker compose build --build-arg` definition.
* **Option struct**: Add `BuildArgs []string` to the `UpOptions` struct in `compose/types/options.go`.
* **Parsing & validation**: Reuse the existing `parseBuildArgs` helper from the `build` command to validate `KEY=VALUE` syntax and to deduplicate entries.
* **Orchestration changes**: In `service/orchestrator.go`, when `opts.Build` is true, invoke `service.Build(ctx, ServiceBuildOptions{BuildArgs: opts.BuildArgs, ...})` before container creation. The build call uses the Docker SDK's `ImageBuildOptions{BuildArgs: map[string]*string{...}}`.
* **Testing**:
  * Unit test `TestUpCommandParseBuildArgs` verifies flag parsing and error handling.
  * Integration test `TestUpWithBuildArgs` spins up a temporary compose project with a Dockerfile that prints a build‑arg, runs `docker compose up --build --build-arg FOO=bar`, and asserts the container environment contains the expected value.
* **Documentation**: Update the CLI reference page and the `docker-compose.yml` spec docs to include the new flag, with examples.
* **Help output**: Ensure `docker compose up --help` lists `--build-arg` with the same description as the `build` command.

4. Drawbacks
* **Complexity**: Adding flag inheritance introduces a small amount of additional parsing logic, which could increase the maintenance burden.
* **Potential misuse**: Users might rely on `--build-arg` for secrets, inadvertently exposing them in image layers. The documentation will warn against this, but the risk remains.
* **Performance**: Each `up --build` now triggers a build step even if the image is already up‑to‑date; however, Docker's cache mechanisms mitigate the impact.

5. Alternatives
* **Separate CLI command**: Introduce a new command `docker compose up-build` that always builds with arguments. This would add a new entry point but would fragment the UX.
* **Compose file extension**: Allow `build.args` under the service definition to accept CLI overrides via an environment variable. This is less discoverable and requires file changes.
* **No flag**: Keep the status quo and require users to run `docker compose build` first. This maintains simplicity but sacrifices convenience.

6. Unresolved Questions
* Should we support multiple `--build-arg` occurrences (already planned via StringArray) or a comma‑separated list? The current design prefers repeated flags for consistency with other Docker commands.
* How should we handle conflicting arguments when both the compose file and CLI provide the same key? The proposal is to let CLI values override file values, but this needs explicit documentation.
* Do we need to add telemetry to track usage of this flag for future prioritization? This is optional and can be revisited after the feature stabilizes.
