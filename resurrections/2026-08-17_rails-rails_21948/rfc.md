# RFC: CSRF protection prevents some webkit users from submitting forms

Summary
Rails' current CSRF protection relies on a session‑bound authenticity token that is generated once per session. Safari (WebKit) restores pages from the back‑forward cache (bfcache) after a user clears cookies, causing the stored token to become stale while the form still contains the old value. Submissions then fail with a 422 error, breaking user experience for a non‑trivial subset of Safari users. This RFC proposes a backwards‑compatible middleware/engine that introduces per‑form short‑lived tokens, client‑side refresh via the Page Lifecycle "pageshow" event, and graceful fallback on token mismatch. The change is optional, defaults to enabled in production, and leverages Rails 7 per‑form token support and the rack‑csrf gem's token rotation capabilities.

Motivation
1. **User impact** – Safari users lose the ability to submit forms after a session reset, leading to lost conversions and support tickets.
2. **Security** – The existing failure mode is a denial‑of‑service rather than a vulnerability, but the workaround (disabling CSRF protection) would weaken security.
3. **Technical readiness** – Modern WebKit exposes the "pageshow" event with the persisted flag, allowing reliable detection of restored pages. Rails 7 already ships per‑form authenticity tokens and encrypted cookies, and rack‑csrf can rotate tokens on each request.
4. **Maintainability** – Implementing the fix as an engine keeps core Rails unchanged, simplifying future upgrades and allowing projects to opt‑in.

Detailed Design
*Middleware Layer*
- Add `Rails::Csrf::PerFormMiddleware` inserted after `ActionDispatch::Cookies`.
- On every GET that renders a form (`response.content_type == "text/html"` and contains `<form`), generate a cryptographically random token (`SecureRandom.base64(32)`).
- Store the token in an encrypted, signed cookie `csrf_form_<form_id>` with a TTL of 5 minutes.
- Inject a hidden field `<input type="hidden" name="authenticity_token" value="<token>" data-csrf-form-id="<form_id>">` into the form markup via a response body rewrite (using `ActionView::Template::Handlers::ERB` hook).

*Verification Logic*
- On POST/PUT/PATCH/DELETE, the middleware extracts `form_id` from the submitted params, reads the corresponding cookie, and compares it to the submitted token.
- If the token matches, request proceeds. If missing or mismatched, the middleware triggers `request.session[:_csrf_token] = SecureRandom.base64(32)` to rotate the session token, returns HTTP 422 with JSON body `{error: "CSRF token invalid", retry: true}`.

*Client‑Side Refresh*
- Provide a JavaScript asset `rails_csrf_refresh.js` that registers `window.addEventListener('pageshow', e => { if (e.persisted) { fetch('/rails/csrf/refresh', {credentials: 'same-origin'}); } });`.
- Add a lightweight controller `Rails::Csrf::RefreshController#refresh` that responds with `head :ok` after setting a fresh per‑form token via the middleware (no body needed).

*Engine Packaging*
- Create `rails-csrf-per-form` engine with initializer to insert middleware and mount the refresh route under `/rails/csrf`.
- Configuration options: `config.csrf_per_form.enabled = true`, `config.csrf_per_form.token_ttl = 5.minutes`.

*Testing & Documentation*
- Add Capybara specs that simulate Safari bfcache by setting `page.evaluate_script('window.history.back();')` and clearing cookies, asserting that the token is refreshed and the form submits successfully.
- Update Rails guides with a "CSRF protection for Safari bfcache" section, including opt‑out instructions.

Drawbacks
- Slight increase in response size due to per‑form hidden fields and encrypted cookies.
- Additional JavaScript payload (~2 KB) required for the pageshow listener.
- Complexity in middleware body rewriting could interfere with streaming responses; we will limit rewriting to non‑streaming HTML.
- Projects that rely on custom CSRF handling may need to adjust their code to accommodate the new per‑form token cookie.

Alternatives
1. **Disable CSRF for GET‑cached pages** – would weaken security globally and is not acceptable.
2. **Force full page reload on bfcache restore** – could be done via `meta[http-equiv="cache-control"]` but degrades performance and does not guarantee token freshness.
3. **Server‑side token rotation on every request** – would eliminate stale tokens but adds overhead to every request and breaks idempotency expectations.
4. **Patch Safari** – not feasible as a Rails project.
The proposed middleware balances security, performance, and user experience better than the alternatives.

Unresolved Questions
- How should the middleware handle forms generated by third‑party gems that already embed their own authenticity tokens?
- Should the token TTL be configurable per environment (e.g., shorter in production, longer in development)?
- What is the best strategy for handling streaming responses that contain forms?
- Will the encrypted cookie approach conflict with applications that disable cookies entirely?
- Need to confirm that the `pageshow` persisted flag works consistently across iOS Safari, macOS Safari, and WebKit‑based browsers like Chrome on iOS.
