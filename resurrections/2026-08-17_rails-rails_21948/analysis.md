# Analysis: CSRF protection prevents some webkit users from submitting forms

> Rails' CSRF protection currently fails when Safari restores cached pages after session cookie clearance.

**Why it will work now:** Safari's WebKit cache restoration behavior was standardized with iOS 12 and iPadOS 13.

---

## Why It Died

The issue required deep changes to Rails' session handling and token verification, which conflicted with existing security guarantees. At the time, Safari's cache restoration behavior was undocumented and hard to test across platforms. The Rails core team prioritized other security features and lacked bandwidth to implement a robust fix. Community interest was limited, leading to the issue stagnating. Consequently, it was left open without resolution.

## Why 2026 Changes Everything

Modern WebKit (Safari 15+) provides explicit APIs to detect restored pages via the Page Lifecycle events, allowing servers to invalidate stale CSRF tokens. Rails 7 introduced per-form authenticity tokens and encrypted cookies, simplifying token regeneration. Additionally, the rack-csrf gem now supports token rotation on cache hits, making the required mitigation straightforward. These tools directly address the original caching and session loss problem.

## Modern Architecture

Introduce a middleware that intercepts GET requests for forms and attaches a short-lived per-form token stored in encrypted cookies. On POST, the middleware validates the token against the session and, if missing, regenerates a fresh token and returns a 422 with a retry hint. Leverage WebKit's Page Lifecycle 'pageshow' event to trigger a client-side fetch that refreshes the CSRF token when a page is restored from cache. Encapsulate the logic in a Rails Engine to keep core unchanged and allow optional inclusion. Provide configuration flags to enable or disable this behavior per environment, defaulting to enabled in production. Write comprehensive tests using Capybara with Safari emulation and include documentation for developers.
