# RFC: st.tabs: know and control state

1. Summary
Add controllable state to Streamlit's `st.tabs` component. The new implementation will expose `default_selected` and `on_change` arguments, store the active tab index in SessionState, and allow the backend to both read the current tab and programmatically set it. This enables bi‑directional synchronization between the frontend UI and the Python runtime.

2. Motivation
Streamlit users frequently need to coordinate tab selection with other widgets, e.g., navigating to a specific tab after a form submission or reflecting URL parameters in the UI. The current `st.tabs` is purely declarative: the selected tab is determined only by user clicks and cannot be inspected or altered by the Python script. Since Streamlit 1.30 introduced a bi‑directional component API and low‑latency WebSocket transport, we now have the technical foundation to expose tab state without breaking existing semantics. Providing this capability will reduce boilerplate (no need for hidden widgets to proxy state), improve accessibility (screen readers can query the active tab), and align tabs with other stateful widgets such as `st.selectbox` and `st.radio`.

3. Detailed Design
**Frontend Component**
- Create a new React component `TabsWithState` extending the existing `Tabs` UI.
- Props:
  * `labels: string[]` – tab titles (as before).
  * `default_selected?: number` – initial active index; falls back to 0.
  * `on_change?: (index: number) => void` – callback invoked on user click.
- Internally maintain a React state `activeIndex`. On mount, initialize from `default_selected` or from a value received via the component's `value` prop (populated by the backend).
- When a tab is clicked, update `activeIndex`, then call `Streamlit.setComponentValue(activeIndex)` which uses the bi‑directional API to push the new index to the Python side.
- Listen for incoming messages via `Streamlit.onComponentValue` to handle programmatic updates; when a new index arrives, set `activeIndex` accordingly, causing a re‑render.

**Backend Integration**
- Extend `st.tabs` signature to `st.tabs(labels, default_selected=0, key=None, on_change=None)`.
- On first call, store `default_selected` in `st.session_state[key + "_tab_index"]`.
- Register a callback with `ComponentRegistry` so that any value emitted from the frontend updates this SessionState entry.
- During each script rerun, read `st.session_state[key + "_tab_index"]` and pass it as the `value` prop to the component, ensuring the UI reflects backend changes.
- If the user supplies an `on_change` callable, invoke it after the SessionState entry is updated.

**Testing**
- Unit tests for the Python wrapper verifying that SessionState is created, updated, and read correctly.
- End‑to‑end Selenium tests simulating user clicks and backend updates, asserting UI sync.
- Performance benchmark to ensure the additional WebSocket round‑trip stays <10 ms on typical workloads.

4. Drawbacks
- Slight increase in memory usage per tab set (one integer per component).
- Additional complexity in the component lifecycle may introduce edge‑cases when multiple tabs share the same `key` across reruns.
- Users may inadvertently create infinite loops by setting the tab index inside an `on_change` handler without guard conditions.

5. Alternatives
- **Hidden Selectbox Proxy**: Use an invisible `st.selectbox` to store the index and manually sync via callbacks. This avoids a new component but is hacky, adds extra DOM nodes, and breaks the declarative API.
- **URL Query Parameters**: Encode tab selection in the URL and parse on each run. This provides deep‑linking but does not allow backend‑only updates and requires extra routing logic.
- **Custom Component**: Ask users to build their own third‑party component. While flexible, it places the burden on the community and fragments the core API.

6. Unresolved Questions
- How should `st.tabs` behave when the supplied `default_selected` is out of range? (Clamp, raise, or ignore?)
- Should we expose a `reset_on_rerun` flag to optionally clear the stored index on each script rerun?
- What is the best naming convention for the SessionState key to avoid collisions with user‑defined keys?
- Are there any accessibility guidelines (ARIA) that need additional handling when the active tab changes programmatically?
- Should we add optional support for synchronizing tab state across multiple users in a shared session (e.g., Streamlit sharing)?
