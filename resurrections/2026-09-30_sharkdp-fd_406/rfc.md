# RFC: Support multiple --exec <cmd> instances

1. Summary
Add support for multiple `--exec <cmd>` specifications to fd. Each `--exec` can contain a placeholder `{}` that will be replaced by the matched file path. An optional `--print-path` flag will emit the path before each command execution. The change is fully backward‑compatible: a single `--exec` behaves exactly as before, and existing scripts continue to work.

2. Motivation
fd is widely used as a fast, ergonomic alternative to find. Users often chain fd with external tools via `--exec`, but the current implementation only allows a single command and does not expose the matched path in a user‑friendly way. Real‑world use cases include:
- Running different linters on files of different extensions.
- Invoking a custom script that needs both the path and additional context.
- Debugging pipelines where seeing the path alongside the command output is essential.
The lack of multi‑exec support forces users to write wrapper scripts or invoke fd multiple times, which defeats its performance advantage. Rust 1.73 and clap v4 now provide the necessary primitives (environment removal, multiple flag occurrences, and easy path access) to implement this cleanly.

3. Detailed Design
**CLI changes**
- Extend the clap definition: `arg(--exec).multiple_occurrences(true).takes_value(true).value_name("CMD")`.
- Introduce a new struct:
```rust
struct ExecSpec {
    template: String,          // raw command string from the flag
    placeholder: String,       // default "{}"; can be customized via env var FD_EXEC_PLACEHOLDER
}
```
- Parse each `--exec` into an `ExecSpec` and store them in a `Vec<ExecSpec>`.
- Add `--print-path` (`bool`) that, when true, logs the path using the `log` crate at `Info` level.

**Core runner modifications**
- The walkdir iterator now yields `DirEntry` objects with a direct `path()` method; we will capture the `PathBuf` for each match.
- For each matched entry, iterate over the `exec_specs` vector:
  1. Replace every occurrence of the placeholder in `spec.template` with the escaped path string.
  2. Split the resulting command line using `shlex::split` to obtain argv.
  3. Build a `Command` via `std::process::Command::new(argv[0])` and `args(&argv[1..])`.
  4. If `--print-path` is set, call `log::info!("Executing on {}", path.display())` before spawning.
  5. Spawn the command, forward its stdout/stderr, and propagate the exit status as fd currently does.
- Preserve the original behaviour when `exec_specs.len() == 1` and `--print-path` is not set.

**Testing & Documentation**
- Add unit tests for placeholder substitution, multiple exec handling, and the `--print-path` flag.
- Update the man page and README with examples:
  `fd . --exec "echo Found {}" --exec "git add {}" --print-path`
- Ensure CI runs on the minimum supported Rust version (1.73) and on Windows, macOS, Linux.

4. Drawbacks
- Slight increase in binary size due to additional parsing logic and the `shlex` dependency.
- Potential performance impact when many exec specs are provided, as each match now spawns multiple processes. However, this mirrors the explicit intent of the user and can be mitigated by limiting the number of specs.
- Users may rely on the old single‑exec semantics for error handling; now each exec runs independently, so a failure in one does not abort the others unless `--exec-stop-on-error` is later added.

5. Alternatives
- **Single exec with a shell pipeline**: Users could manually chain commands with `&&` or `;`. This is less ergonomic and does not provide per‑command path visibility.
- **Introduce a templating engine**: A full templating language (e.g., handlebars) would be overkill for the simple placeholder use case and increase complexity.
- **Separate subcommand**: `fd exec-multi` could have been added, but extending the existing `--exec` flag keeps the UI surface minimal and intuitive.

6. Unresolved Questions
- Should we support custom placeholders per `--exec` (e.g., `{path}`, `{basename}`) or keep a single global placeholder? Initial implementation uses a single placeholder for simplicity; future extensions may add named variables.
- How should exit codes be aggregated? Currently fd returns the highest non‑zero code among all execs; we need to confirm this aligns with user expectations.
- Do we need a flag to control ordering (sequential vs parallel exec of multiple specs)? For now, execution is sequential to preserve deterministic output.
