# RFC: proposal: must: Do

Summary
Introduce a new helper function `url.MustParse(s string) *url.URL` and a generic utility `must.Do[T any](fn func() (T, error)) T` to the Go standard library. The helpers eliminate repetitive error‑checking boilerplate when parsing URLs or invoking functions that return a value and an error, panicking on failure in a controlled, documented manner. The proposal leverages Go 1.20 generics and recent vet enhancements to keep the API surface small while providing ergonomic, type‑safe error handling.

Motivation
The current pattern for parsing URLs is:

    u, err := url.Parse(raw)
    if err != nil {
        panic(err)
    }

Repeated throughout code bases, this boilerplate obscures intent and adds noise. A `MustParse` helper mirrors existing `regexp.MustCompile` and `template.Must` patterns, offering a familiar, concise alternative. Earlier attempts were rejected due to concerns about API bloat and unchecked panics. Since Go 1.20, generics enable a single, reusable `must.Do` that can cover any function returning `(T, error)`, reducing the need for a proliferation of `Must*` functions. Additionally, go vet now flags ignored errors, encouraging developers to adopt explicit handling; a well‑documented `must` package provides a safe, vetted escape hatch for cases where a panic is acceptable (e.g., initialization code, test fixtures, or command‑line tools). Adding these helpers as a minor stdlib change aligns with the language’s evolution toward ergonomics without sacrificing safety.

Detailed Design
1. **Package `net/url`**
   - Add `func MustParse(s string) *URL`.
   - Implementation: call `Parse(s)`; if `err != nil` panic(err).
   - Document that it should only be used where a malformed URL is a programmer error (e.g., constant literals).
2. **New package `must`** (public, stdlib)
   - File `must/do.go`:
     ```go
     package must

     // Do calls fn, panicking if fn returns a non‑nil error.
     // The generic type parameter T is the successful return type.
     func Do[T any](fn func() (T, error)) T {
         v, err := fn()
         if err != nil {
             panic(err)
         }
         return v
     }
     ```
   - Provide examples in the package doc showing usage with `url.Parse`, `json.Unmarshal`, database queries, etc.
3. **Tests**
   - `net/url/mustparse_test.go` covering valid URLs (returns non‑nil URL) and invalid URLs (expects panic via `defer recover`).
   - `must/do_test.go` exercising generic behavior with different types (int, struct, pointer).
4. **Vet Integration**
   - Add a `vet` check that recognizes `must.Do` as an intentional ignore of the error return, preventing false positives.
5. **Documentation & Release Notes**
   - Update `net/url` docs with a `MustParse` example.
   - Add a `must` package doc page.
   - Include a bullet in Go 1.XX release notes: "Added url.MustParse and generic must.Do for ergonomic error handling."

Drawbacks
- Introducing panics into library code can be misused; developers may over‑rely on `must.Do` for production error handling, leading to crashes.
- Slight increase in the stdlib surface area (new package, new function) which modestly raises maintenance burden.
- Existing code that manually checks errors will not automatically migrate; the change is opt‑in only.

Alternatives
1. **Leave the status quo** – keep manual error checks; no API change, but boilerplate remains.
2. **Add only `url.MustParse`** – avoid the generic `must.Do`; this reduces surface area but misses the broader ergonomics gain.
3. **Create a `must` subpackage in `golang.org/x/tools`** – externalizes the helper, avoiding stdlib bloat, but loses the guarantee of vet integration and official documentation.

Unresolved Questions
- Should `must.Do` be exported as `must.Do` or placed under an existing package like `internal/must` with a public alias? Exporting provides discoverability but may encourage misuse.
- What naming convention best fits the Go style guide? `must.Do` mirrors `sync.Once.Do`; alternatives like `must.Call` were considered.
- How strict should vet be about flagging `must.Do` usage in production code? A configurable vet flag may be needed.
- Will future Go releases add more `Must*` helpers, and if so, how will we guard against uncontrolled API growth?
