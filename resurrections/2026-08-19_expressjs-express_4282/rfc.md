# RFC: Dependencies (5.0)

1. Summary
Express 5.0 will drop all legacy third‑party utilities (methods, path‑is‑absolute, safe‑buffer, setprototypeof, utils‑merge) and replace them with native Node.js APIs. A new internal module `@expressjs/core-utils` will re‑export the built‑ins, providing a single import surface for the framework. The change is gated by a runtime feature flag that falls back to the old packages on Node <14, preserving compatibility for legacy deployments.

2. Motivation
The current Express 4.x codebase pulls in five small but unnecessary dependencies. Each adds install‑time overhead, duplicate maintenance, and potential security surface area. Since Node 14 LTS, the core provides stable equivalents for all of these utilities, and the project has migrated to TypeScript, making large‑scale refactoring safer. Removing the dependencies will:
- Reduce bundle size and install time.
- Eliminate duplicated logic that can drift from Node's behavior.
- Simplify the security audit surface.
- Align Express with modern Node.js best practices and improve developer ergonomics.
The original effort stalled due to lack of a dedicated champion and concerns about breaking older Node versions. With Node 14+ now the minimum supported version for Express 5.0, those concerns are mitigated.

3. Detailed Design
**Core Utilities Module**
Create `src/core-utils.ts` that exports:
```ts
export { METHODS as httpMethods } from 'node:http';
export { isAbsolute as pathIsAbsolute } from 'node:path';
export const bufferFrom = Buffer.from;
export const bufferAlloc = Buffer.alloc;
export const setProto = Object.setPrototypeOf;
export const merge = (target: any, ...sources: any[]) => Object.assign(target, ...sources);
```
**Methods Replacement**
Replace `require('methods')` with a lazy wrapper:
```ts
import { httpMethods } from '@expressjs/core-utils';
export const methods = httpMethods.map(m => m.toLowerCase());
```
**Path‑is‑Absolute**
All occurrences of `require('path-is-absolute')` become `import { pathIsAbsolute } from '@expressjs/core-utils';` and calls are unchanged.
**Safe‑Buffer**
Replace `new SafeBuffer(... )` with `Buffer.from` or `Buffer.alloc` as appropriate. Types are enforced via TypeScript overloads.
**SetPrototypeOf**
Replace `setPrototypeOf(req, prototype)` with `setProto(req, prototype)`. Guard with `if (typeof setProto === 'function')` for older runtimes (should never trigger under Node >=14).
**Utils‑Merge**
Replace `utilsMerge(a, b)` with `{ ...a, ...b }`. For deep merges, a small internal helper using recursion will be added, typed with generics.
**Compatibility Shim**
Add `src/legacy-shim.ts` that conditionally imports the old packages when `process.env.EXPRESS_LEGACY_DEPS=1` or when `process.version` < 'v14.0.0'. The main code paths import from `@expressjs/core-utils` first, falling back to the shim.
**Testing**
- Add unit tests for each utility wrapper.
- Run the existing test matrix on Node 14, 16, 18, and 20.
- Verify that the public API (`express.request`, `express.response`) remains unchanged.

4. Drawbacks
- The change raises the minimum supported Node version to 14, breaking users still on Node 12.
- Introducing a runtime flag adds a small amount of complexity to the build and CI pipelines.
- Some edge‑case behavior (e.g., Buffer subclassing quirks) may differ subtly; extensive regression testing is required.

5. Alternatives
- Keep the dependencies but pin them to exact versions; this would avoid breaking older Node releases but would not achieve the size and security benefits.
- Incrementally deprecate each package over several minor releases, providing deprecation warnings; this spreads the effort but prolongs the cleanup.
- Fork the external packages and maintain a minimal internal copy; this reduces external risk but reintroduces maintenance burden.

6. Unresolved Questions
- Should we expose the new `@expressjs/core-utils` module as a public API for downstream libraries, or keep it internal?
- How will the compatibility shim handle future Node versions that deprecate certain core APIs?
- Is there a need for a migration guide for existing Express 4.x applications that rely on the exact semantics of the old packages?
- What is the policy for handling user‑reported regressions that stem from subtle differences in Buffer handling?
- Will the TypeScript declaration files need to be versioned separately to avoid breaking downstream type consumers?
