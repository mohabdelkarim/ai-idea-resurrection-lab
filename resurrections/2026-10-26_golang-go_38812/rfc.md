# RFC: cmd/go: "package … is not in GOROOT" is confusing in module mode when the package would exist in GOPATH mode

Summary
The go command currently reports "package … is not in GOROOT" when a package cannot be found, regardless of whether the user is operating in module mode or GOPATH mode. In module mode, the presence of a go.mod file silently overrides GOPATH, which can lead to confusing diagnostics for developers who expect GOPATH semantics. This RFC proposes to augment the error message with explicit context indicating that module mode overrides GOPATH, e.g., "package … is not in GOROOT (module mode overrides GOPATH)". The change will be implemented by adding a lightweight detection API in cmd/go/internal/modload, extending the error construction path in cmd/go/internal/work, and updating the errlist template. Unit tests and a go1.21+ build tag will ensure correctness and backward compatibility.

Motivation
The existing error message is ambiguous and often leads developers to waste time checking GOROOT or reinstalling packages. The confusion is most acute for developers transitioning from GOPATH‑centric workflows to module‑centric ones, or for CI environments that still rely on GOPATH layout. Since Go 1.21 introduced richer module diagnostics and exposed APIs for module vs GOPATH detection, we now have the infrastructure to provide clearer feedback with minimal invasive changes. Improving ergonomics aligns with Go's philosophy of simplicity and developer productivity, and it reduces the volume of duplicate bug reports and support tickets related to this misunderstanding.

Detailed Design
1. **API addition**: In cmd/go/internal/modload, introduce `func ModuleModeOverridesGOPATH(dir string) (bool, error)` that walks up from `dir` to locate a go.mod file. It returns true if a go.mod is found and the current build is in module mode.
2. **Error path extension**: Modify cmd/go/internal/work's `func NewImportError(pkgPath string, err error) error` to accept an optional context string. If `ModuleModeOverridesGOPATH` returns true, pass the context "module mode overrides GOPATH".
3. **Template update**: In cmd/go/internal/errlist, add a placeholder `%{context}` to the package‑not‑found template. The final rendered message will be:
   `package %s is not in GOROOT%{context}` where `%{context}` expands to " (module mode overrides GOPATH)" when applicable.
4. **Build tag**: Guard the new code with `//go:build go1.21` to keep Go 1.20 and earlier unaffected.
5. **Testing**: Add `cmd/go/internal/modload/modload_test.go` with two test cases: (a) a temporary directory containing a go.mod file, expecting the context flag true; (b) a directory without go.mod, expecting false. Also add integration tests in `cmd/go/internal/work` to verify the formatted error string.
6. **Documentation**: Update the cmd/go error messages section in the Go command documentation to mention the new context.

Drawbacks
* Slight increase in compile time for the cmd/go package due to the additional file system walk when constructing errors. However, this path is only exercised on failure cases, which are rare in normal builds.
* Introduces a new public‑ish internal function, marginally expanding the surface area of the internal/modload package. The function is deliberately kept internal to avoid API churn.
* Requires a go1.21+ build tag; older toolchains will not see the improved message, which could lead to inconsistent developer experiences across versions.

Alternatives
1. **No change** – Keep the status quo; developers must infer module mode from other cues. This preserves simplicity but leaves the confusion unresolved.
2. **Separate command flag** – Introduce a `-show-mod-override` flag that, when set, prints the extra context. This adds user‑level complexity and requires remembering an extra flag.
3. **Generalized error enrichment** – Refactor the entire error handling system to carry rich metadata for all errors. While powerful, this is a large undertaking beyond the scope of this targeted improvement.
The proposed solution balances minimal invasiveness with tangible ergonomics gains.

Unresolved Questions
* Should the context be appended to all "not in GOROOT" style errors, or only to those triggered from `go get`/`go install`? The current design applies it universally, but we may need to refine the scope based on future feedback.
* Is the phrasing "module mode overrides GOPATH" the most user‑friendly wording? Alternative phrasing such as "module-aware mode, GOPATH ignored" could be considered after community review.
* Do we need to expose the detection API for external tools (e.g., IDEs) to reuse? At present it remains internal, but a future public API could be beneficial.
