# RFC: Add ability to duplicate row with all panels

1. Summary
Add a first‑class "duplicate row" capability to Grafana dashboards. A new REST endpoint (/api/dashboards/{uid}/rows/{rowId}/duplicate) will invoke a RowDuplicationService that deep‑copies the target Row struct, clones each contained Panel via the existing PanelService, and inserts the new Row at a user‑specified position. The UI will expose a "Duplicate Row" action in the row context menu, guarded by a feature flag (rowDuplicationEnabled) for staged rollout. The implementation leverages Grafana 10's declarative dashboard model and Go 1.22 generics to perform safe deep copies of nested structs.

2. Motivation
Users frequently need to reuse a set of panels that share layout, datasource bindings, and alert rules. Currently they must manually recreate each panel or copy‑paste panels one‑by‑one, which is error‑prone and time‑consuming. Providing a row‑level duplication streamlines dashboard authoring, reduces configuration drift, and aligns Grafana with competitor products that already support this workflow. The technical blockers that prevented this feature in the past (absence of a unified Row abstraction and lack of deep‑copy utilities) have been removed by the new panel library and Go generics, making the effort low‑risk and high‑value.

3. Detailed Design
* Backend Service
  - Introduce `RowDuplicationService` in `pkg/services/dashboard/rowduplication.go`.
  - Method signature: `func (s *RowDuplicationService) Duplicate(ctx context.Context, dashboardUID string, rowID int64, targetIndex int) (int64, error)`.
  - Retrieve the dashboard via `DashboardService.GetByUID` and locate the Row struct.
  - Use a generic deep‑copy helper `deepcopy.Copy[T any](src T) T` to clone the Row metadata (title, collapse state, gridPos, etc.).
  * Panel Cloning
    - Iterate over `row.Panels`, calling `PanelService.ClonePanel(ctx, panelID, newDashboardUID)` which already copies queries, thresholds, and alert definitions.
    - Append the cloned panels to the new Row's `Panels` slice.
  * Insertion
    - Insert the new Row into `dashboard.Rows` at `targetIndex` (or after the original if not specified).
    - Persist the updated dashboard via `DashboardService.Update`.
    - Return the newly created Row ID.
* REST Endpoint
  - Add handler `POST /api/dashboards/{uid}/rows/{rowId}/duplicate` in `pkg/api/dashboard.go`.
  - Payload: `{ "targetIndex": int }` (optional).
  - Respond with `{ "newRowId": int64, "message": "Row duplicated successfully" }`.
* UI Changes
  - Extend `RowHeader` component to include a "Duplicate" button in the context menu.
  - Call the new endpoint, refresh the dashboard model on success.
* Feature Flag
  - Register `rowDuplicationEnabled` in `pkg/featuremgmt/flags.go` with default `false`.
  - Guard both backend handler registration and UI button visibility.
* Tests
  - Unit tests for `RowDuplicationService` covering deep copy integrity, panel ID remapping, and insertion order.
  - Integration test exercising the REST endpoint with a mock dashboard.
  - End‑to‑end UI test using Cypress to verify the button appears and the duplicated row renders correctly.
* Documentation
  - Update `docs/sources/dashboards/provisioning.md` with a "Duplicating rows" section.
  - Add a changelog entry and release notes.

4. Drawbacks
* Increased dashboard size: Duplicating rows can lead to large dashboards if users repeatedly copy complex rows, potentially impacting load performance.
* Permission surface: The operation writes new panels; existing permission checks must ensure the caller has edit rights on the dashboard.
* Migration complexity: Older dashboards stored rows as flat panel lists; the service must handle legacy formats gracefully, adding conditional logic that slightly increases code paths.

5. Alternatives
* Panel‑only duplication: Keep the existing "duplicate panel" feature and encourage users to group panels manually. This avoids new backend code but does not solve the workflow pain point.
* Export‑Import shortcut: Provide a JSON export of a row that users could paste back. This is clunky, requires manual editing, and offers a poorer UX.
* Full dashboard templating: Introduce a templating system to reuse row definitions across dashboards. While powerful, it is a larger scope than the immediate duplication need and would delay delivery.

6. Unresolved Questions
* Should the duplicated row inherit the original's collapse state or always start expanded?
* How should alert rule IDs be handled when panels are cloned – should they be duplicated as new alerts or reference the same alert?
* Is there a need for a limit on the number of rows that can be duplicated in a single request to prevent abuse?
* Will the feature be enabled by default in the next major release, or remain behind a flag for an extended beta period?
