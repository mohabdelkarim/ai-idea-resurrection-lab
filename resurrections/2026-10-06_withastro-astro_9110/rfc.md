# RFC: Cannot destructure react component props

1. Summary
Implement a robust prop forwarding and validation layer in Astro's React integration to prevent destructuring of undefined component props. The change introduces a wrapper that maps incoming Astro props to React component props using the new `props` API, adds runtime guards, updates TypeScript definitions, and provides migration guidance.

2. Motivation
Astro projects that embed React components currently suffer from runtime errors when a component attempts to destructure props that were not supplied by the parent. The root cause is that Astro's integration simply spreads `props` onto the React component without guaranteeing their presence, and TypeScript definitions do not flag missing fields. This leads to crashes that are hard to debug, especially in production builds where Vite 4 provided limited diagnostics. With Astro 3.6, Vite 5, TypeScript 5.3, and React 18.3 now offering better prop handling and error reporting, we can close this gap, improve developer experience, and increase reliability of mixed‑framework sites.

3. Detailed Design
* **Wrapper Update**: Extend `AstroComponent` (src/integrations/react/index.ts) to create a `ReactPropForwarder` that receives the raw `props` object from Astro, filters it against the component's prop type metadata (extracted via `Component.propTypes` or TS interface via `tsx` compiler API), and constructs a new object `forwardedProps`.
* **Runtime Guard**: Insert a guard function `validateProps(componentName, forwardedProps, requiredKeys)` that throws a descriptive `AstroReactPropError` if any required key is `undefined`. The guard is only active in development (`import.meta.env.DEV`).
* **Vite Plugin Hook**: Leverage Vite 5's `transform` hook to inject the guard code during dev builds, ensuring zero impact on production bundle size.
* **TypeScript Declarations**: Add `declare module "astro/react"` with generic `ReactComponent<Props>` that enforces `Props` extends `Record<string, any>` and marks required keys as non‑optional. Update `astro.d.ts` to re‑export these types.
* **Testing**: Create unit tests in `tests/react/prop-forwarding.test.ts` covering:
  - Simple prop forwarding
  - Missing required prop triggers runtime error in dev
  - Optional props omitted without error
  - Integration test using Astro test runner with a sample page rendering a React component.
* **Documentation**: Revise `integrations/react/README.md` with a "Prop Forwarding" section, migration steps (add `export const runtime = "edge"` if needed), and examples.

4. Drawbacks
* Introduces a small runtime overhead in development due to validation checks.
* Requires pulling in `prop-types` or a lightweight metadata extraction library, adding to the integration bundle size (≈3 KB gzipped).
* Projects that relied on the previous permissive behavior may need to add missing props or mark them optional, causing a minor migration effort.

5. Alternatives
* **Silent Ignoring**: Simply ignore undefined props, letting destructuring yield `undefined`. This avoids crashes but hides bugs and provides a poor developer experience.
* **Compile‑time Only**: Rely solely on improved TypeScript inference without runtime guards. This would catch many issues but not all, especially when props are supplied dynamically at runtime.
* **Full PropTypes Enforcement**: Enforce strict `prop-types` validation for every React component. This would be more heavyweight and duplicate functionality already present in React 18.3.

6. Unresolved Questions
* How should the integration handle `defaultProps` defined on class components versus function components with default parameters?
* Should the guard also warn about extra props that are not declared in the component's type?
* Is there a need to expose a configuration flag (`react.validateProps`) to allow users to disable validation in large dev environments?
* Compatibility with future Astro compiler optimizations (e.g., partial hydration) needs verification.
