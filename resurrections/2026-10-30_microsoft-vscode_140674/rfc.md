# RFC: Allow to place tabs at the bottom

1. Summary
VSCode will introduce a new configurable option, `workbench.editor.tabPlacement`, allowing users to position the editor tab bar either at the top (default) or at the bottom of the workbench. The implementation leverages Electron 30's stable region‑manipulation API and the newly added declarative layout contribution point, requiring only modest changes to the existing TabBar component and layout service. This RFC details the design, migration path, and testing strategy.

2. Motivation
The current UI forces the tab bar to the top of the editor area, limiting ergonomics for users who prefer a bottom‑oriented workflow (e.g., those coming from IDEs like IntelliJ or from mobile‑first design patterns). Historically the feature was blocked by deep coupling between the tab renderer and the workbench layout, and by the lack of a flexible extension point. With Electron 30's custom title‑bar APIs and VSCode's recent modular CSS‑in‑JS refactor, repositioning core UI elements can be achieved without invasive forks, preserving performance and cross‑platform consistency. Providing a bottom tab placement improves accessibility (easier reach for large monitors), satisfies a long‑standing user request, and showcases the new layout contribution system.

3. Detailed Design
* Configuration Schema: Add `workbench.editor.tabPlacement` to `package.json` under `contributes.configuration`. Type: string enum ["top", "bottom"], default "top".
* Layout Service Extension: Extend `WorkbenchLayoutService` to read the setting on startup and on change events. Introduce a new container `bottomTabContainer` within the main workbench grid (CSS grid area `bottom-tab`).
* TabBar Component: Reuse existing `TabBar` and `TabRenderer`. When the placement is "bottom", the layout service mounts the `TabBar` instance into `bottomTabContainer`; otherwise it remains in the existing `topTabContainer`.
* Styling: Add themable CSS class `tabBarBottom` that switches the grid row/column placement and adjusts overflow handling. The CSS‑in‑JS system will generate the appropriate styles at runtime, ensuring themes can override colors without breaking layout.
* Accessibility: Preserve ARIA roles (`role="tablist"`, `role="tab"`) and keyboard navigation (Ctrl+Tab, arrow keys). The focus order is updated to reflect the new DOM position.
* Settings UI: Add a dropdown in Settings UI under "Workbench > Editor: Tab Placement".
* Tests: Unit tests for `WorkbenchLayoutService` verifying container selection; integration tests that open multiple editors, toggle the setting, and assert visual placement via DOM queries. Add e2e tests for keyboard navigation in both placements.
* Documentation: Update Settings Reference, add a migration note for theme authors about the new `tabBarBottom` class, and include screenshots.

4. Drawbacks
* Slight increase in layout complexity: an extra container and conditional mounting adds a few lines of code and a minor runtime check on every setting change.
* Potential visual regressions on very small screens where the bottom area may clash with the status bar; mitigated by responsive CSS that collapses the bottom tab bar into a scrollable overflow.
* Some extensions that directly query the tab bar DOM may need to handle the new location; however, the public API (`IEditorGroupsService`) remains unchanged.

5. Alternatives
* Keep tabs only at the top and provide a separate "bottom panel" with a custom extension that mimics tabs. This would avoid core changes but would result in duplicated functionality and inconsistent UX.
* Implement a draggable tab bar that users could move freely. This would be more flexible but requires a substantial redesign of the drag‑and‑drop infrastructure and is out of scope for the current release cycle.
* Use a vertical side‑tab layout (left/right). This is already partially supported via the "sideBar" and is a different UX paradigm, not a direct replacement for bottom placement.

6. Unresolved Questions
* How should the bottom tab bar interact with the existing panel toggle button (the "View" icon) when the panel is hidden? Should the button move into the bottom container or stay at the top?
* Will there be any impact on multi‑monitor setups where the workbench is stretched horizontally? Need performance testing on low‑end GPUs.
* Should we expose a future enum value "auto" that automatically chooses placement based on screen height? This is a possible extension but not required for the initial implementation.
