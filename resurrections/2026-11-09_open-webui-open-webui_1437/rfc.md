# RFC: feat: Tier 1 support for LocalAI

Summary
The purpose of this RFC is to add native Tier‑1 support for LocalAI to the open‑webui codebase. By introducing a generic Provider abstraction and a concrete LocalAIProvider implementation, open‑webui will be able to route chat, completion, text‑to‑speech (TTS), speech‑to‑text (STT), and image generation requests to a LocalAI server via its stable OpenAI‑compatible REST API and official TypeScript SDK. The change includes UI extensions for provider selection, configuration schema updates, and a full test suite.

Motivation
LocalAI has matured since the original issue was filed. Version 0.5 (released early 2026) ships a stable OpenAI‑compatible endpoint and an official TypeScript SDK, eliminating the earlier barrier of an experimental API. open‑webui’s plugin system was refactored to use a Provider interface, making it straightforward to plug in new back‑ends. Adding LocalAI now offers several concrete benefits:
1. Users can run a fully local LLM stack with chat, completions, TTS, STT, and image generation without relying on external cloud services.
2. It expands open‑webui’s market reach to privacy‑focused communities and edge deployments.
3. It aligns with the broader ecosystem trend where LangChain and other libraries already provide first‑class LocalAI adapters.
4. It leverages existing infrastructure (Docker, configuration UI) to keep implementation effort low.

Detailed Design
1. Provider Interface
   ```ts
   export interface Provider {
     chat(messages: Message[]): AsyncIterable<ChatChunk>;
     complete(prompt: string, opts?: CompletionOpts): Promise<string>;
     tts(text: string, opts?: TTSOpts): Promise<Buffer>;
     stt(audio: Buffer, opts?: STTOpts): Promise<string>;
     generateImage(prompt: string, opts?: ImageOpts): Promise<string[]>; // URLs or base64
   }
   ```
2. LocalAIProvider Implementation
   - Uses `@localai/sdk` (the official TypeScript client).
   - Constructor receives `{ apiKey: string; baseUrl: string; model: string }` from configuration.
   - Each method forwards calls to the SDK, handling streaming via `for await` loops and converting SDK errors into a unified `ProviderError` type.
3. Configuration Schema
   - Extend `src/config/schema.ts` with `localAI: { enabled: boolean; apiKey: string; baseUrl: string; model: string }`.
   - UI Settings panel adds a collapsible section for LocalAI, with validation for URL format and optional API key.
4. UI Integration
   - Add a provider dropdown in `ChatHeader` allowing selection among "OpenAI", "Ollama", "LocalAI", etc.
   - The selected provider key is stored in user preferences and passed to the request dispatcher which resolves the appropriate Provider instance.
5. Error Mapping
   - Map LocalAI error codes (e.g., `RATE_LIMITED`, `MODEL_NOT_FOUND`) to open‑webui toast notifications with human‑readable messages.
6. Testing
   - Unit tests mock `@localai/sdk` using `jest.mock` to verify method contracts.
   - Integration tests spin up a LocalAI Docker container (`docker run -p 8080:8080 localai/localai:0.5`) and run end‑to‑end scenarios for each capability.
   - CI pipeline adds a matrix job for the LocalAI integration.

Drawbacks
- Adding another provider increases the maintenance surface; future breaking changes in the LocalAI SDK will require coordinated updates.
- Users must manage a separate LocalAI service, which may increase deployment complexity for non‑technical users.
- The UI now contains an additional dropdown, marginally increasing visual clutter.

Alternatives
1. **Proxy via Existing OpenAI Provider**: Treat LocalAI as a generic OpenAI endpoint without a dedicated Provider class. This would reduce code but lose type‑safe SDK benefits and make error handling less precise.
2. **Community‑Only Plugin**: Ship the integration as an optional plugin rather than core code. This would keep the core lean but would require users to install and maintain the plugin manually, reducing discoverability.
3. **Delay Until v0.6**: Wait for a future LocalAI release with built‑in authentication flows. This would postpone benefits and miss the current momentum.

Unresolved Questions
1. **Authentication Model**: LocalAI currently supports optional API keys; should the UI enforce a key or allow empty values for fully open deployments?
2. **Model Discovery**: Should the provider expose a dynamic list of available models from the LocalAI server, or rely on a static default?
3. **Resource Limits**: How should open‑webui surface LocalAI resource constraints (CPU/GPU usage) to the user, if at all?
4. **Telemetry**: Do we need to add opt‑in telemetry to capture usage patterns of the LocalAI provider for future optimization?
