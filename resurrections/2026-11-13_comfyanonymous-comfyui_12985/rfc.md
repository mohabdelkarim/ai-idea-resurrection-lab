# RFC: Feedback on update frequency and stability

1. Summary
ComfyUI will introduce a dedicated stable release channel backed by a 'stable' branch, automated CI/CD pipelines, and semantic versioning. Only code that passes a comprehensive compatibility test suite will be merged into this branch, and the desktop application will allow users to lock to the latest stable tag. This reduces breaking changes for active users while preserving rapid development on the main branch.

2. Motivation
The current development workflow prioritizes feature velocity over reliability. Frequent breaking changes in the main branch have caused user frustration, especially for those who rely on custom nodes in production pipelines. Lack of automated regression testing and a formal release policy means that even minor API tweaks can render existing workflows unusable. Since 2024, GitHub Actions, pytest, tox, and semantic‑release have matured, providing the tooling needed to enforce backward compatibility without slowing down contributors. Providing a stable channel will:
- Increase user confidence and adoption in commercial settings.
- Lower the support burden on maintainers by reducing ad‑hoc breakage reports.
- Encourage third‑party node developers to target a known API surface.

3. Detailed Design
a. Branch Strategy
   - `main`: continues as the fast‑track development branch.
   - `stable`: protected branch that only receives merges after passing the stability pipeline.
   - Release tags follow Semantic Versioning (MAJOR.MINOR.PATCH).

b. CI Workflow (GitHub Actions)
   - On every PR to `stable`, run:
     * Unit tests (pytest) across Python 3.9‑3.12.
     * Integration tests against a curated list of the top 20 community nodes.
     * Compatibility matrix using tox to simulate older ComfyUI versions.
   - A pre‑commit hook enforces linting, type checking (mypy), and docstring standards.
   - If all jobs succeed, the PR can be merged.

c. Compatibility Manifest
   - A `plugin_manifest.yaml` in the repo enumerates supported node APIs with version constraints.
   - The CI pipeline parses this file and fails if any public API change violates the declared constraints.

d. Automated Release
   - semantic‑release is configured to watch the `stable` branch.
   - When a merge lands and the pipeline passes, a PATCH version is automatically published to PyPI and a GitHub release is created.
   - MAJOR or MINOR bumps require a manual “release‑candidate” label on the PR.

e. Desktop Application Integration
   - Add a settings toggle: “Use Stable Channel”. When enabled, the app fetches updates only from the latest stable tag.
   - Provide a fallback to the last known stable version if the current stable fails health checks.

f. Documentation & Migration Guides
   - Update the README with the new release policy.
   - Create a `MIGRATION.md` outlining API deprecations and recommended node updates.

4. Drawbacks
   - Maintaining two active branches doubles the merge overhead for maintainers.
   - The curated integration test list may not cover every niche custom node, leaving edge‑case regressions possible.
   - Initial setup of CI pipelines and the compatibility manifest requires significant effort and may delay upcoming feature releases.

5. Alternatives
   - **Single‑branch with feature flags**: Keep only `main` and gate breaking changes behind runtime flags. This reduces branch complexity but still exposes users to potential breakage.
   - **Long‑term support (LTS) releases**: Freeze a point-in-time snapshot of the codebase for a year. This provides stability but limits the ability to back‑port bug fixes without extensive cherry‑picking.
   - **Community‑driven testing harness**: Invite external contributors to run compatibility tests on their own CI. This distributes load but lacks enforceable guarantees.

6. Unresolved Questions
   - How large should the curated integration test suite be, and how will we keep it up‑to‑date with community node evolution?
   - What policy will govern deprecation warnings and the timeline for removing legacy APIs?
   - Should we provide a separate “beta” channel for users who want early access but still want some stability guarantees?
   - How will we handle version pinning for downstream projects that embed ComfyUI as a submodule?
   - What metrics will we collect to assess the impact of the stable channel on user satisfaction and issue volume?
