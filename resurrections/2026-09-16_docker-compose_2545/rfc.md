# RFC: Proposal: support for args_file

Summary
Docker Compose will introduce a new top‑level service option `args_file` that allows users to specify one or more external files containing build‑time arguments (VAR=VAL). The files are parsed similarly to Docker's `--build-arg` mechanism, merged with any inline `args` entries, and passed to BuildKit via the existing secret handling pipeline. This RFC outlines the motivation, design, trade‑offs, alternatives, and open questions.

Motivation
The current Compose specification only supports inline `args` and environment files for runtime variables. Large projects often maintain build arguments in separate files to keep secrets out of version control and to simplify CI pipelines. Without native support, users resort to shell scripts or custom wrappers, which duplicate logic and break composability. Since Docker 18.09, BuildKit provides a secure API for injecting secret files, and Compose v2’s modular configuration parser now easily accommodates new keys. Implementing `args_file` will:
- Align Compose with Docker CLI’s `--secret` and `--build-arg` patterns.
- Reduce boilerplate in CI/CD configurations.
- Improve security by keeping secrets out of compose YAML.
- Provide a clear, documented way to manage build arguments across multiple services.

Detailed Design
1. **Configuration Model**: Add `ArgsFile []string` to the `ServiceConfig` struct in libcompose, mirroring `EnvFile`. The field accepts a list of relative or absolute file paths.
2. **YAML Parsing**: Extend the Go parser to recognise the `args_file` key. Paths are resolved against the directory containing the compose file, using the same logic as `env_file`.
3. **File Format**: Each file contains newline‑separated `KEY=VALUE` pairs, supporting comments (`#`). Blank lines are ignored. Duplicate keys within a file are resolved by the last occurrence.
4. **Merging Logic**:
   - Parse all files in the order listed.
   - Merge resulting map into the service’s `BuildArgs` map.
   - Inline `args` entries in the compose file take precedence over file‑derived values.
5. **BuildKit Integration**: During the `docker compose build` command, the aggregated argument map is passed to the BuildKit client via the existing `BuildOptions.Args` field. For values marked as secrets (e.g., prefixed with `secret:`), the secret handling pipeline is used to inject them as temporary files, ensuring they are not persisted in the image.
6. **Testing**:
   - Unit tests for parser handling of `args_file`, precedence rules, and error cases (missing file, malformed line).
   - Integration test that runs a minimal BuildKit‑enabled daemon, builds a service with an `args_file`, and verifies the resulting image contains the expected ARG values.
7. **Documentation**: Update the Compose reference docs and CLI help to include `args_file` with examples for both plain arguments and secret‑backed arguments.

Drawbacks
- **Complexity**: Adds another source of build arguments, increasing the mental model required for debugging builds.
- **Security Surface**: If users mistakenly commit argument files containing secrets, they may be exposed. However, this risk mirrors existing practices with `.env` files and can be mitigated with .gitignore.
- **Compatibility**: Older Compose versions will ignore the key, potentially leading to silent failures in mixed‑environment teams.

Alternatives
1. **Reuse `env_file` for build args**: Not feasible because `env_file` is scoped to runtime environment, not build time, and Docker treats them differently.
2. **CLI‑only `--build-arg-file` flag**: Would require users to modify scripts rather than declarative compose files, reducing portability.
3. **External pre‑processing step**: Users could generate a composed `args` map via templating tools, but this adds external dependencies and defeats the purpose of a native feature.

Unresolved Questions
- Should `args_file` support other serialization formats (JSON, YAML) in addition to the simple `KEY=VAL` syntax?
- How should conflicts between multiple files be reported? Currently we adopt “last‑win” but may need a warning flag.
- Is there a need for a per‑argument secret flag (e.g., `my_secret=secret:my_secret`) or should secret handling be inferred from BuildKit’s secret API?
- What is the best default behavior when a file is missing? Fail fast vs. ignore with a warning.
- Should we expose a `--args-file` CLI override for ad‑hoc builds?
