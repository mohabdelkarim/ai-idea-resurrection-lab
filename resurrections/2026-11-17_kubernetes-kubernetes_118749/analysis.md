## Why It Died

When the issue was opened, the scheduler lacked a pluggable framework to evaluate pods across namespace boundaries, making the change invasive. The existing TopologySpreadConstraints API only accepted same‑namespace pods, and extending it required core scheduler refactoring that the SIG Scheduling team prioritized lower. Limited maintainer bandwidth and concerns about breaking existing scheduling semantics delayed any implementation. Additionally, there was no feature gate to safely experiment with cross‑namespace spreading, causing the proposal to stall.

## Why 2026 Changes Everything

Kubernetes 1.28 introduced a mature scheduler framework with plugin support, allowing new predicates without rewriting the core. The CrossNamespaceSpread feature gate, added in 1.29, explicitly enables topologySpreadConstraints to consider pods from other namespaces. client-go 0.30 provides generated types for the extended TopologySpreadConstraints spec, simplifying controller updates. Go 1.22’s generics and embed support make the plugin code cleaner and easier to test. These concrete changes remove the technical blockers that existed in 2023.

## Modern Architecture

Implement a new scheduler plugin named CrossNamespaceSpread that registers during scheduler initialization. The plugin reads the extended TopologySpreadConstraints field, which now includes a boolean crossNamespace flag. It queries the shared informer cache for pods across all namespaces, filtering by the selector defined in the constraint. The scoring function calculates node scores based on pod counts, respecting existing maxSkew and topologyKey semantics. The plugin respects the CrossNamespaceSpread feature gate, allowing gradual rollout. Tests use the scheduler-framework testing harness and mock informers to validate distribution across namespaces. Documentation updates add the new flag to the API reference and scheduling guide.
