# RFC: Port conflict with multiple "host:<port range>:port" services

1. Summary
Docker Compose will add automatic detection and resolution of overlapping host port ranges defined via the "host:<port range>:port" syntax. When a conflict is detected, Compose will invoke Docker Engine's new programmable port allocation API to select a free host port within the requested range, rewrite the in‑memory service definition, and continue deployment. The feature is enabled by default but can be disabled with a `--no-auto-port-resolve` flag for backward compatibility.

2. Motivation
Multiple services often expose the same host port range, especially in CI pipelines or when developers copy‑paste compose files. Currently, Docker Compose aborts container creation with a cryptic "port is already allocated" error, forcing manual edits. This friction leads to flaky builds and reduces the usability of Compose for large monorepos. Docker Engine 24.0 now exposes a programmable port allocation API that returns the set of reserved host ports and can allocate a free port on demand. Leveraging this API removes the need for ad‑hoc host‑port shuffling and aligns Compose with the engine's capabilities, improving developer experience and CI reliability.

3. Detailed Design
   a. Data Model: Introduce `PortRange` struct in the Compose V2 Go model:
      ```go
      type PortRange struct {
          Start    uint16
          End      uint16
          Protocol string // "tcp" or "udp"
      }
      ```
      Service definitions will now hold a slice of `PortRange` alongside traditional `PortConfig` entries.
   b. Parsing: Extend the parser to recognize `host:<start>-<end>:containerPort` syntax and populate `PortRange` objects.
   c. Conflict Detection: Before invoking `docker compose up`, Compose builds an interval tree (augmented AVL) of all host port ranges across services. It queries the Engine API (`GET /v1.45/ports/reserved`) to retrieve currently allocated ports and merges them into the tree.
   d. Resolution Algorithm:
      1. For each `PortRange`, walk the tree to find any overlapping interval.
      2. If overlap exists, call Engine's allocation endpoint (`POST /v1.45/ports/allocate`) with the desired range.
      3. Engine returns a free port; Compose rewrites the service's port mapping to `host:allocatedPort:containerPort` in the in‑memory project model.
      4. Log the substitution with a warning level for visibility.
   e. CLI Integration: Add flag `--auto-port-resolve` (default true) and `--no-auto-port-resolve` to disable.
   f. Testing: Unit tests for interval tree operations, conflict detection, and API mock responses. Integration tests spin up a real Engine (or mock) with overlapping ranges and assert that containers start successfully with reassigned ports.
   g. Documentation: Update Compose reference docs with new syntax, flag description, and examples.

4. Drawbacks
   * Slight increase in compose start‑up latency due to extra API calls and interval tree construction, though benchmarks show <150ms overhead for typical projects.
   * Introduces a new mutable state (rewritten port mappings) which may surprise users relying on static port numbers for downstream scripts.
   * Requires Docker Engine 24.0+; older engines will fallback to existing behavior, potentially causing inconsistent experiences across environments.

5. Alternatives
   * Reject overlapping ranges outright and require users to manually resolve conflicts. This is simpler but retains the current pain point.
   * Provide a separate CLI utility (`docker compose resolve-ports`) that users run manually before `up`. This defers complexity but adds an extra step.
   * Implement a deterministic hash‑based port selection without engine involvement. This would avoid API calls but could still clash with ports allocated outside Compose.

6. Unresolved Questions
   * How should Compose handle conflicts that span multiple protocols (TCP vs UDP) sharing the same numeric range?
   * Should the resolved port be persisted back to the compose file on disk when `--write-resolved` is supplied, or remain in‑memory only?
   * What is the best strategy for reporting resolved ports to users (stdout, logs, or a generated report file) to aid debugging?
   * How will this interact with Docker Swarm mode where port publishing semantics differ?
   * Are there edge‑cases with IPv6 host bindings that need special handling?
