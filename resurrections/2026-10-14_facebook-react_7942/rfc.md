# RFC: Fiber Principles: Contributing To Fiber

1. Summary
This RFC proposes adding a first‑class, version‑controlled documentation set for React's internal Fiber architecture. The documentation will live under a new `docs/fiber` directory, be generated from TypeScript type definitions, and be kept in sync via CI. It will include design pattern guides, traversal diagrams, and contribution guidelines aimed at onboarding contributors to safely work with Fiber internals.

2. Motivation
React 18 introduced concurrent rendering and a public Scheduler API, dramatically increasing the visibility of Fiber's role in the rendering pipeline. At the same time, DevTools now expose Fiber nodes, and `@types/react` ships typed definitions for the Fiber structures. These advances lower the risk of exposing internal design patterns and create a strong demand for authoritative, maintainable documentation. Current knowledge is scattered across code comments, blog posts, and occasional talks, which makes onboarding new contributors slow and error‑prone. A structured guide will:
- Reduce bugs caused by incorrect Fiber mutations.
- Accelerate feature development by providing a clear reference.
- Enable community contributions to core internals with confidence.
- Preserve institutional knowledge as the core team evolves.

3. Detailed Design
**Directory Layout**
```
react/
├─ docs/
│  └─ fiber/
│     ├─ overview.md
│     ├─ traversal.md
│     ├─ patterns.md
│     └─ contribution.md
├─ scripts/
│  └─ generateFiberDocs.ts
└─ src/
   └─ ... (Fiber implementation)
```
**FiberSchema Class**
- Create `src/internal/FiberSchema.ts` that re‑exports the public TypeScript interfaces (`Fiber`, `FiberRoot`, `Lanes`, etc.) and adds JSDoc comments describing each field.
- The class is never used at runtime; it exists solely for documentation generation.
**Doc Generation Script**
- `scripts/generateFiberDocs.ts` will import `FiberSchema`, walk the type tree using the TypeScript compiler API, and emit markdown files.
- It will also run a small runtime traversal of a sample Fiber tree (using the singly‑linked list pattern `child -> sibling -> return`) to produce ASCII diagrams inserted into `traversal.md`.
**CI Integration**
- Add a step in the existing CI workflow: `npm run generate:fiber-docs && git diff --exit-code docs/fiber`. If differences are found, the build fails, forcing a documentation update before merging.
**Contribution Guide**
- `contribution.md` will codify the accepted mutation patterns: only mutate Fibers inside `beginWork` and `completeWork`, use the `tag` enum with a `switch` dispatch, and never directly modify the `return` pointer outside of the reconciliation phase.
- Provide a checklist for reviewers to verify compliance.

4. Drawbacks
- **Maintenance Overhead**: The generation script adds a build step and requires the TypeScript compiler to stay compatible with internal changes.
- **Potential Leakage**: Exposing more internal detail could encourage external code to rely on undocumented behavior, increasing the surface for breaking changes.
- **Initial Effort**: Writing the initial markdown, diagrams, and tests will require several weeks of core team time.

5. Alternatives
- *Keep status‑quo*: Rely on existing comments and occasional blog posts. This avoids maintenance cost but leaves the onboarding problem unsolved.
- *Separate Wiki*: Host the guide in a community‑maintained wiki. Lower integration friction but loses the guarantee of being in sync with code.
- *Inline Docs Only*: Add richer JSDoc comments directly in the source without separate markdown. Improves discoverability but makes navigation harder for newcomers.

6. Unresolved Questions
- How much of the internal API should be considered stable enough to document publicly? Should we mark certain sections as “internal‑only” with a disclaimer?
- What is the preferred format for the generated diagrams (ASCII vs SVG)? Which toolchain offers the best trade‑off for CI speed?
- Should the documentation be versioned per major React release, or can we rely on a single moving target?
- How will we handle contributions from external developers who may not have the same internal knowledge? Should we require a sign‑off from a core maintainer for any Fiber‑related doc change?
