# RFC: Store metrics docstrings and allow to query them

1. Summary
Prometheus will be extended to store metric HELP strings (and type information) as first‑class metadata and expose them via a new /api/v1/metadata endpoint. The implementation introduces a MetricMetadata struct, an in‑memory map keyed by the metric identifier, and a lightweight BoltDB sidecar that persists metadata alongside the existing TSDB blocks. Query clients can retrieve HELP strings for any metric, and the UI will display them next to graphs. This RFC details the design, migration path, and impact.

2. Motivation
Historically Prometheus only retained HELP strings in memory for the lifetime of a scrape, discarding them during persistence. Users increasingly rely on the HELP text for observability, alerting, and automated documentation. The OpenTelemetry Metric Metadata standard (2023) now mandates a HELP field, and the remote‑write protocol (v2.0, 2024) already transports this metadata. Go 1.22’s struct tag enhancements make it trivial to embed arbitrary strings in persisted structures. Without native storage, exporters must duplicate HELP strings in external docs, leading to drift and confusion. Providing a reliable, queryable source of HELP strings will improve usability, enable richer UI experiences, and align Prometheus with the broader observability ecosystem.

3. Detailed Design
   a. Data Model: Define `type MetricMetadata struct { Name string; Help string; Type string; UpdatedAt int64 }`. Instances are stored in a global `metadataMap map[uint64]*MetricMetadata` where the key is the internal series identifier.
   b. Write Path Integration: During sample ingestion, the remote‑write parser extracts any attached metadata and updates `metadataMap`. Updates are batched per TSDB block and flushed to a BoltDB sidecar file (`metadata.db`) using a single atomic transaction per block, ensuring no additional latency for sample writes.
   c. Persistence Layout: Each TSDB block directory will contain a `metadata.db` file. The BoltDB bucket `metadata` maps series IDs to protobuf‑encoded `MetricMetadata`. On block load, the sidecar is opened and the map is repopulated.
   d. API Endpoint: Add `/api/v1/metadata?metric=<name>` which returns JSON `{ "status":"success", "data": { "<metric>": { "help":"...", "type":"...", "last_updated":"..." } } }`. The handler reuses the existing query router and marshals from `metadataMap`.
   e. UI Integration: The Graph UI will request metadata for displayed series and render the HELP string as a tooltip and in the legend.
   f. Conflict Resolution: If multiple scrapes provide differing HELP strings for the same metric, the system logs a warning and applies a last‑write‑wins policy based on `UpdatedAt`. A Prometheus alert rule template is provided to surface frequent conflicts.
   g. Testing: Unit tests for the metadata parser, BoltDB persistence, and API serialization. Integration tests using the OpenTelemetry exporter will verify end‑to‑end flow from exporter → remote‑write → storage → API.

4. Drawbacks
   * Additional disk usage: each HELP string (typically a few hundred bytes) is stored per series, increasing block size modestly (estimated <5% for typical workloads).
   * Slightly more complex block loading logic, requiring error handling for missing or corrupted `metadata.db` files.
   * Potential for stale HELP strings if exporters change documentation without bumping metric names; the last‑write‑wins policy may hide regressions.

5. Alternatives
   * Store HELP strings only in memory and expose via `/api/v1/labels` – rejected because metadata would be lost on restart.
   * Encode HELP strings into the existing TSDB WAL entries – rejected due to high write amplification and impact on ingestion latency.
   * Provide a separate sidecar service that aggregates HELP strings from exporters – rejected as it adds operational complexity and breaks the single‑binary philosophy of Prometheus.

6. Unresolved Questions
   * How should we handle metrics that intentionally change HELP text across versions (e.g., deprecation notices)? Should we version the HELP field?
   * What retention policy should apply to metadata? Should it be tied to block retention or have a separate TTL?
   * Is BoltDB the optimal choice for sidecar storage, or would a simple append‑only file be sufficient for future scalability?
   * Should we expose a bulk endpoint to retrieve metadata for all metrics in a block for large‑scale dashboards?
   * How will this feature interact with federation, where remote read may request metadata from downstream instances?
