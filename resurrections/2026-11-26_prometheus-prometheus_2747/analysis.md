# Analysis: Store metrics docstrings and allow to query them

> Prometheus should store metric HELP strings and expose them through its query API.

**Why it will work now:** OpenTelemetry metric metadata standardization (2023) enables unified docstring handling across monitoring tools.

## Why It Died

The original proposal required changes to Prometheus's on‑disk format, which lacked a dedicated metadata section. Implementing it would have increased write latency and storage overhead for a feature that few users requested at the time. The core team prioritized scaling and reliability over UI enhancements, and community contributors were focused on other high‑priority issues. Additionally, there was no standardized way to represent HELP strings across different exporters, leading to inconsistent data.

## Why 2026 Changes Everything

The OpenTelemetry metric metadata standard (2023) now defines a uniform HELP field that exporters already emit. Prometheus's remote‑write protocol was extended in 2024 to carry metric metadata alongside samples. Go 1.22 introduced improved struct tag handling and embed directives, simplifying storage of arbitrary strings in the TSDB. These tools collectively remove the technical blockers that prevented the feature in 2017.

## Modern Architecture

Introduce a new MetricMetadata struct containing name, help string, and type, stored in an in‑memory map keyed by metric identifier. Extend the TSDB write path to persist metadata in a lightweight bolt‑DB sidecar, ensuring atomic updates without impacting sample ingestion performance. Add a /api/v1/metadata endpoint that returns JSON objects with HELP strings, leveraging existing query handlers. Update the UI component to fetch and display this metadata alongside metric graphs. Implement conflict resolution by logging a warning when differing HELP strings are observed and applying a last‑write‑wins policy. Provide unit tests and integration tests using the new OpenTelemetry exporter to verify end‑to‑end metadata flow.
