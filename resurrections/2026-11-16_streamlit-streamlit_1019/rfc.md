# RFC: Add directory chooser

1. Summary
Streamlit will add a new UI component called `st.directory_chooser` that enables users to select a folder from their local file system. The component leverages the now‑standard `<input type="file" webkitdirectory>` HTML attribute to provide native folder selection across Chrome, Edge, and Firefox. On the Python side, the selected folder is represented as a `pathlib.Path` object and its contents are streamed lazily via the existing pluggable file‑manager API introduced in Streamlit 1.30. The widget supports optional parameters such as `recursive_depth`, `file_type_filter`, and `preview_callback` to give developers fine‑grained control over what is presented to the user and how the data is processed.

2. Motivation
Folder selection is a common requirement for data‑science and ML workflows, where users often need to upload entire datasets, image collections, or model checkpoints. Previously, developers resorted to multiple `st.file_uploader` calls or custom JavaScript hacks, leading to fragmented UX and increased code complexity. Modern browsers now provide consistent folder‑selection capabilities, and Streamlit's recent file‑manager overhaul makes it feasible to expose a high‑level abstraction without breaking backward compatibility. Adding this widget will reduce boilerplate, improve user experience, and align Streamlit with other data‑app frameworks that already support directory uploads.

3. Detailed Design
**Frontend**
- Implement a React component `DirectoryChooser` extending `StreamlitWidget`.
- Render `<input type="file" webkitdirectory multiple>` with optional `accept` attribute derived from `file_type_filter`.
- On change, collect the `FileList`, preserve relative paths (`file.webkitRelativePath`), and send a protobuf message containing:
  * `root_name` (the folder name)
  * `files` array of `{relative_path, size, mime_type, content_base64}`
- If `preview_callback` is provided, invoke it with a thumbnail generated from the first few files.

**Backend**
- Extend `FileManager` with `handle_directory_upload(message)` which:
  1. Creates a temporary directory on the server.
  2. Writes each received file to the temp location preserving the relative hierarchy.
  3. Returns a `pathlib.Path` pointing to the root of the temporary directory.
- Provide a lazy async generator `stream_directory(path, depth)` that yields `pathlib.Path` objects for each file up to `recursive_depth`.
- Expose the widget API:
```python
st.directory_chooser(
    label: str,
    recursive_depth: int = -1,
    file_type_filter: List[str] | None = None,
    preview_callback: Callable[[List[pathlib.Path]], Any] | None = None,
) -> pathlib.Path | None
```
- The function returns `None` until a folder is selected.

**Testing & Documentation**
- Add integration tests using Playwright for Chrome, Edge, and Firefox to verify folder selection, filter enforcement, and depth limiting.
- Unit tests for `FileManager.handle_directory_upload` and `stream_directory`.
- Documentation pages with examples: loading a CSV dataset folder, batch image preprocessing, and streaming large log directories.

4. Drawbacks
- Temporary storage of potentially large directory trees may increase disk usage on the Streamlit server, requiring cleanup mechanisms.
- Security considerations: uploading executable files could be risky; we must enforce server‑side validation or sandboxing.
- The widget relies on the `webkitdirectory` attribute, which, while widely supported, is not part of the official HTML spec and could be deprecated in future browser releases.

5. Alternatives
- **Multiple file uploader**: Users could select many files individually, but this loses folder hierarchy and is cumbersome for deep trees.
- **Custom JavaScript bridge**: Implement a bespoke file‑system picker via the File System Access API; however, it lacks cross‑browser parity and would increase maintenance burden.
- **Server‑side zip upload**: Ask users to zip folders before upload; this adds an extra manual step and requires decompression logic.
Each alternative either reduces usability or adds complexity compared to the native folder picker.

6. Unresolved Questions
- How should Streamlit handle extremely large uploads (e.g., >5 GB)? Should we introduce streaming uploads or size limits?
- What is the optimal cleanup strategy for temporary directories—per‑session, per‑widget, or background garbage collector?
- Should we expose additional security hooks (e.g., virus scanning) as part of the widget API?
- Will future browsers replace `webkitdirectory` with a standardized attribute, and how will we migrate without breaking existing apps?
