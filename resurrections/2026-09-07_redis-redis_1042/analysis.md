# Analysis: Allow to set an expiration on hash field

> Redis should support setting expiration times directly on individual hash fields.

**Why it will work now:** Redis 7.0 introduced modular command extensions and improved keyspace notifications, enabling per-field expirations.

---

## Why It Died

The core Redis data model only tracks expiration at the key level, lacking internal structures for per-field timers. Implementing field-level TTL would require changes to the RDB/AOF persistence format, which was deemed too invasive at the time. The Redis community prioritized other features and the maintainer bandwidth was limited, so the proposal was left untouched.

## Why 2026 Changes Everything

Redis 7.0 introduced a modular command framework and enhanced keyspace notification APIs, making it easier to hook custom expiration logic. The new module system allows developers to add per-field metadata without altering the core server code. Additionally, the improved RDB/AOF handling now supports custom data types, enabling safe persistence of field-level TTLs.

## Modern Architecture

Create a new module named redis-hash-ttl that registers a subcommand HSETEX to set a field with a TTL. Internally, extend the hash object with a lightweight dictionary mapping fields to expiration timestamps. Use the existing server cron loop to check and evict expired fields, reusing the key expiration scheduler. Update the RDB/AOF serializers to write the field‑TTL map alongside the hash data, leveraging the module serialization callbacks. Add keyspace notification events "hfieldexpire" to inform clients of field expirations. Provide a compatibility layer that forwards legacy EXPIRE calls to the new subcommand when a field argument is present.
