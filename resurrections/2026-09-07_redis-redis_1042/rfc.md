# RFC: Allow to set an expiration on hash field

1. Summary
Redis currently supports expiration only at the key level. This RFC proposes a new module, **redis-hash-ttl**, that introduces per‑field expiration for hash data structures. The module adds a subcommand `HSETEX key field value TTL` to set a field with an explicit time‑to‑live, stores expiration timestamps in a lightweight per‑hash field‑TTL map, integrates with the server's cron loop for eviction, updates RDB/AOF serialization via module callbacks, and emits a new keyspace notification event `hfieldexpire`. The goal is to enable fine‑grained cache semantics while preserving backward compatibility with existing hash commands.

2. Motivation
Many workloads use a single Redis hash as a namespace for many related items (e.g., user sessions, product attributes). When only key‑level TTL is available, the entire hash must be evicted to expire a single stale field, leading to unnecessary data loss and higher churn. Per‑field TTL would allow:
- Precise cache invalidation for individual entries without affecting siblings.
- Reduced memory pressure by automatically cleaning up obsolete fields.
- Simplified application logic, eliminating the need for auxiliary structures (e.g., separate keys per field).
Redis 7.0 introduced a robust module API, including custom data types and serialization hooks, making it feasible to embed field‑level metadata without invasive core changes. Moreover, the enhanced keyspace notification system can now broadcast custom events, allowing clients to react to field expirations.

3. Detailed Design
**Module Architecture**
- Register a new data‑type `hashWithTTL` that wraps the native hash object and adds a `dict *field_expire` mapping field strings to 64‑bit UNIX timestamps.
- Provide command `HSETEX key field value ttl_ms` (TTL in milliseconds). The command validates the key type, creates the wrapper if needed, stores the field/value using the native hash API, and inserts `field -> now+ttl_ms` into `field_expire`.
- Implement `HGETEX key field` to return the value only if the field has not expired; otherwise, behave as a miss.

**Expiration Scheduler**
- Hook into the server's `activeExpireCycle` via `moduleTimer` that runs every 100ms. It iterates over all `hashWithTTL` objects, checks the earliest expiration in `field_expire`, and deletes expired fields using the native hash deletion API. Deletions trigger the `hfieldexpire` notification.

**Persistence**
- Use module serialization callbacks: `rdbSave` writes the underlying hash data followed by the `field_expire` dictionary (field name + 8‑byte timestamp). `rdbLoad` reconstructs both structures. AOF rewrite appends `HSETEX` commands for each field with a non‑zero TTL.

**Compatibility Layer**
- The module registers a command alias `EXPIRE key field seconds` that internally forwards to `HSETEX` when a third argument is detected, preserving existing scripts that may have used a custom convention.

**Keyspace Notifications**
- Emit `hfieldexpire` with the format `__keyspace@<db>__:key field` so subscribers can monitor per‑field expirations.

4. Drawbacks
- Additional memory overhead: each field now stores an 8‑byte timestamp plus dict overhead.
- Expiration scanning adds CPU load proportional to the number of hash fields with TTLs; in pathological cases (millions of fields) this could impact latency.
- Persistence size grows because TTL metadata must be stored alongside field data, increasing RDB/AOF size.
- Introducing a new module type may fragment the ecosystem if not adopted widely; users must load the module explicitly.

5. Alternatives
- **Application‑level TTL**: Store timestamps as part of the field value and have clients check them. This avoids server changes but shifts logic to clients and cannot trigger automatic eviction.
- **Separate keys per field**: Use `SETEX` for each item. Guarantees native TTL handling but loses the compactness and atomicity of hashes.
- **Core modification**: Extend the Redis core to support per‑field TTL natively. This would avoid a module layer but requires a major codebase change and extensive testing, which the core team currently deems too risky.

6. Unresolved Questions
- What is the optimal scanning interval for the expiration loop to balance latency vs. CPU usage?
- How should the module handle replication and cluster slot migration for `hashWithTTL` objects? Should the field‑TTL map be sent as part of the regular hash sync or via separate messages?
- Should we expose a command to query remaining TTL for a field (`HPTTL key field`)?
- How will the module interact with Redis' lazy expiration (when a key is accessed) – should field checks be performed lazily as well?
- Are there any security considerations for exposing per‑field TTL metadata to untrusted clients?
