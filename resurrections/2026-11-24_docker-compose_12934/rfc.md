# RFC: Support for Apple Containers

1. Summary
Docker Compose will add native support for Apple’s Linux container engine (Apple Containers) on macOS. A new pluggable engine provider, `AppleEngineProvider`, will be introduced to satisfy the existing Compose Engine interface, allowing users to select the "apple" driver in their compose files or CLI. This RFC describes the design, integration points, and migration path, leveraging Docker Engine 24.0's stable Apple runtime API and Go 1.22 embed.FS improvements.

2. Motivation
The macOS developer experience has long relied on Docker Desktop’s heavyweight VM, causing performance overhead and licensing friction. Apple’s native container runtime, now stable as of Docker Engine 24.0, offers lightweight, hardware‑accelerated Linux containers directly on macOS. Providing first‑class Compose support unlocks faster iteration cycles, reduces resource consumption, and aligns Compose with the broader Docker ecosystem’s move toward pluggable back‑ends. The previous attempt failed due to an unstable API and limited maintainer bandwidth; the current platform maturity and engine architecture changes make the effort feasible and valuable for the community.

3. Detailed Design
* **EngineProvider struct**: Implement `type AppleEngineProvider struct { client *appleapi.Client }` that satisfies `Engine` methods `Start(ctx, svc) error`, `Stop(ctx, svc) error`, `Status(ctx, svc) (State, error)`, and `Exec(ctx, svc, cmd []string) (ExecResult, error)`.
* **API client**: Use the stable endpoint `POST /v1/apple/containers` etc., provided by Docker Engine 24.0. The client will be generated via OpenAPI and wrapped for retry/back‑off.
* **Configuration schema**: Extend the Compose schema (`compose-spec.yml`) with a top‑level `x-apple:` block and a service‑level `driver: apple` field. Validation rules added to `loader/validator.go` ensure mutual exclusivity with other drivers.
* **Registry integration**: In `engine/registry.go`, register the provider with `registry.Register("apple", NewAppleEngineProvider)`. Selection occurs during CLI parsing when `--driver apple` or `driver: apple` is present.
* **Embedding runtime binaries**: Leverage Go 1.22 `embed.FS` to bundle the small Apple runtime shim binary within the Compose binary, simplifying distribution without external downloads.
* **Testing**: Add unit tests in `engine/apple_test.go` using `httptest.Server` to mock Apple API responses. Include integration tests guarded by the `APPLE_INTEGRATION` build tag.
* **CLI & docs**: Add `--driver apple` flag to `docker compose up`, update `docker compose --help`, and create a new docs page `docs/compose/apple-driver.md` with usage examples.

4. Drawbacks
* **Platform limitation**: The feature only works on macOS 14+ where Apple Containers are supported, adding a conditional code path that must be maintained.
* **Increased binary size**: Embedding the shim adds ~2 MB to the Compose binary, which may be undesirable for minimal installations.
* **Operational parity**: Not all Docker Engine features (e.g., swarm mode, secret management) are currently exposed via the Apple runtime, so some Compose commands will fallback or error, requiring clear user messaging.

5. Alternatives
* **External wrapper script**: Instead of a native provider, ship a wrapper that translates Compose commands to `docker` CLI calls targeting the Apple runtime. This would avoid code changes but adds latency and complexity for users.
* **Wait for Docker Desktop integration**: Defer support until Docker Desktop bundles Apple Containers natively, eliminating the need for a separate provider. This would delay the benefits and keep the current heavyweight VM.
* **Community plugin**: Publish the Apple provider as an external Go plugin rather than core Compose code. However, plugin loading adds runtime overhead and complicates distribution.

6. Unresolved Questions
* How should Compose handle features that are unsupported by Apple Containers (e.g., `docker compose push` for registries)? Will we provide graceful degradation or explicit errors?
* What is the upgrade path for existing projects that specify `driver: docker` but run on macOS? Should we auto‑detect and suggest switching to `apple`?
* Are there licensing implications for bundling the Apple shim binary within the Compose distribution?
* How will we coordinate versioning of the Apple API client with Docker Engine releases to avoid mismatches?
* Should we expose additional Apple‑specific configuration options (e.g., resource limits) in the Compose schema, and if so, how will they be validated?
