# RFC: Actioncable Webpacker compilation issues with Rails 6 in production

Summary
The proposal introduces a dedicated ActionCableWebpackerAdapter that modernizes the integration of ActionCable assets with Webpacker 6 in Rails 6 production environments. The adapter will hook into Webpacker’s compile lifecycle, apply Babel transformations, and generate import‑map entries when appropriate. A new configuration initializer will allow developers to toggle between Webpacker‑based bundling and import‑map loading, ensuring reliable asset compilation on platforms such as Heroku. Comprehensive tests, documentation updates, and a rake validation task accompany the change.

Motivation
ActionCable asset compilation has been flaky in production for Rails 6 apps that rely on Webpacker 5. The root cause is an outdated build pipeline that fails to polyfill the `_typeof` helper and does not support deterministic hashing introduced in Webpacker 6. This leads to runtime errors on Heroku and other PaaS providers, breaking real‑time features. Since Rails 7 now ships with import‑map support and esbuild integration, the ecosystem has proven that a more flexible approach is feasible. Updating the Rails 6 codebase to leverage Webpacker 6 and import‑maps will eliminate the historical compilation breakage, reduce maintenance overhead, and align Rails 6 with current JavaScript tooling.

Detailed Design
1. **ActionCableWebpackerAdapter class**
   - Located at `lib/action_cable_webpacker_adapter.rb`.
   - Registers a `webpacker:compile:before` hook via `Webpacker::Compiler`.
   - Reads `node_modules/@rails/actioncable` source, runs Babel preset‑env targeting `>0.25%, not dead` browsers, and injects a custom `_typeof` polyfill if missing.
   - Emits the transformed bundle to `public/packs/action_cable.js` with deterministic hash (e.g., `action_cable-<hash>.js`).
2. **Import‑map generation**
   - During the same hook, generates an entry in `config/importmap.rb` like `pin "@rails/actioncable", to: "action_cable-<hash>.js"`.
   - If the `import_map` mode is disabled, the adapter falls back to the traditional Webpacker pack reference.
3. **Configuration initializer**
   - Add `config/initializers/action_cable.rb` exposing `Rails.application.config.action_cable.asset_mode = :webpacker | :importmap`.
   - Default to `:webpacker` for backward compatibility.
4. **Rake task**
   - `rake action_cable:verify_build` runs a local production compile (`RAILS_ENV=production bin/webpack`) and checks that the generated bundle contains the `_typeof` helper and correct export.
5. **Testing**
   - RSpec integration specs under `spec/integration/action_cable_webpacker_spec.rb` simulate a Heroku slug compilation using `ENV['RAILS_ENV']=production` and assert the presence of the hash‑named file and import‑map entry.
6. **Documentation**
   - Update the Rails Guides section “Action Cable and Asset Pipeline” with a new subsection describing the adapter, configuration options, and troubleshooting steps.

Drawbacks
- Introduces additional Ruby code and a compile‑time dependency on Babel, increasing the Rails 6 gem footprint.
- Projects that have heavily customized Webpacker configs may need minor adjustments to avoid hook conflicts.
- The import‑map fallback adds a small runtime overhead for browsers that must fetch the generated pack instead of a pre‑compiled asset.

Alternatives
1. **Patch Webpacker 5** – Attempt to backport the missing polyfills and deterministic hashing. This would require maintaining a fork of Webpacker, which is deprecated and lacks community support.
2. **Full migration to Rails 7** – Encourage users to upgrade, but many legacy Rails 6 applications cannot move immediately due to gem constraints.
3. **External build script** – Provide a separate Node‑only script to compile ActionCable assets. This would duplicate logic already present in Webpacker and increase operational complexity.
Each alternative either postpones the fix, adds maintenance burden, or forces a major version upgrade, making the adapter approach the most balanced solution.

Unresolved Questions
- How will the adapter behave with custom Babel configurations defined by the host application? Should we merge or override them?
- Should we support Yarn 3 lockfile formats automatically, or require explicit migration steps?
- Is there a need for a fallback for Ruby versions older than 2.7, given that some Rails 6 apps still run on Ruby 2.5?
- The exact set of browsers to target for the Babel preset‑env needs consensus; we propose the current Rails default but may need adjustment based on user feedback.
