# RFC: wrapping by word would be awesome

1. Summary
Add a new word‑aware wrapping mode to bat. The mode will be selectable via a new `--wrap word` flag (or `--wrap=word`) and will prevent words from being split across lines. The implementation will rely on the stable `unicode-segmentation` crate (v1.10) to obtain Unicode word boundaries, and will be integrated into bat's existing rendering pipeline without breaking current behaviour. By default bat continues to use the existing character‑wise wrap, preserving backward compatibility.

2. Motivation
The current wrap implementation in bat operates on a byte/character basis, which can split words and produce unreadable output, especially for long prose, documentation snippets, or log messages. Users have repeatedly requested a word‑aware wrap to improve readability. Previously the feature was blocked by the lack of a reliable Unicode segmentation library and the tight coupling of the wrap logic to low‑level byte handling. Since `unicode-segmentation` now offers a stable API for iterating over Unicode words, and clap v4 supports enum arguments, the technical barriers have been removed. Adding this mode will make bat more useful as a pager for natural‑language text and will align it with other modern tools (e.g., `less -S` with word wrap). It is a low‑risk, high‑value enhancement that does not affect core syntax‑highlighting functionality.

3. Detailed Design
* **API changes**: Introduce an enum `WrapMode { Char, Word }` in `config.rs`. Extend the CLI definition in `cli.rs` to accept `--wrap <MODE>` where `<MODE>` is either `char` (default) or `word`. Clap's `arg_enum!` macro will automatically generate the parser.
* **Configuration**: Add a field `wrap_mode: WrapMode` to the `Config` struct. The default is `WrapMode::Char` to preserve existing behaviour.
* **Rendering pipeline**: Modify `renderer.rs` to accept `wrap_mode` as a parameter. For `WrapMode::Char` delegate to the existing `wrap_charwise` function. For `WrapMode::Word`, implement `wrap_wordwise` which:
  1. Uses `unicode_segmentation::UnicodeSegmentation::unicode_words` to split the input line into an iterator of `&str` word slices.
  2. Iteratively appends words to a buffer, inserting a space when needed, and checks the rendered width using `unicode_width::UnicodeWidthStr::width` against the terminal column count.
  3. When adding a word would exceed the width, flush the current buffer as a line and start a new one.
  4. Handles edge cases: very long words (longer than the width) fall back to character‑wise breaking for that word to avoid infinite loops.
* **Configuration file**: Update `bat.conf` documentation to allow `--wrap=word` as a persistent setting.
* **Tests**: Add unit tests in `tests/wrap.rs` covering:
  - Pure ASCII text.
  - Multibyte UTF‑8 characters (e.g., accented letters).
  - Emoji and zero‑width joiner sequences.
  - Extremely long single words.
* **Documentation**: Update the man page, `README.md`, and `--help` output to describe the new mode and its default.
* **Performance**: Benchmark both modes; word‑wise wrapping adds O(n) overhead for segmentation but remains well within bat's typical latency (<5 ms for 10 kB input).

4. Drawbacks
* **Complexity increase**: Introducing a new code path adds maintenance overhead and a potential source of bugs, especially around edge‑case Unicode handling.
* **Performance penalty**: Word segmentation is more expensive than the current byte‑wise approach, which could be noticeable on extremely large files or on low‑end hardware.
* **Behavioral change**: Users may encounter different line breaks than before, which could affect scripts that rely on exact output layout.

5. Alternatives
* **Hybrid mode**: Instead of a full word‑wise mode, implement a heuristic that only avoids splitting words longer than a threshold. Rejected because it would still require Unicode word detection and would be less predictable.
* **External pager**: Recommend using `less -S` with `--RAW-CONTROL-CHARS` for word wrap. Rejected because it does not integrate with bat's syntax highlighting.
* **Post‑processing filter**: Provide a separate utility (`bat-wrap`) that rewraps bat's output. Rejected as it adds friction and duplicates functionality.

6. Unresolved Questions
* How should we handle combining characters that are not word separators (e.g., diacritics) when computing width? The current `unicode_width` crate handles most cases, but edge cases may need special testing.
* Should we expose an option to disable the fallback to character‑wise breaking for overly long words, or to truncate them? This could be added in a later patch.
* Is there a need for a `--wrap=none` mode to disable wrapping entirely, or is that already covered by `--paging=never`? The decision will be revisited based on user feedback.
