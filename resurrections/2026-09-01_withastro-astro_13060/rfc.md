# RFC: Aastro preview doesn't respect vite preview allowedHostnames in astro config

1. Summary
Astro's `preview` command should honor Vite's `allowedHosts` setting defined in the Astro configuration file. This RFC proposes adding a configuration bridge that maps `astro.config.vite.preview.allowedHosts` (and related preview options) to Vite's preview server, ensuring that host validation works as expected during local preview.

2. Motivation
The current implementation launches Vite's preview server with default host validation, ignoring any `allowedHosts` configuration supplied by the user. This leads to two practical problems:
* Developers working behind reverse proxies or with custom hostnames cannot preview their site without disabling host checks, reducing security and developer ergonomics.
* The omission is a regression risk because Vite 5 now exposes a unified preview API, and Astro v5.2 already supports passing arbitrary Vite preview options, yet the bridge is missing.
By fixing this, Astro aligns with Vite's expectations, improves developer experience, and future‑proofs the preview pipeline against upcoming Vite releases.

3. Detailed Design
* **Config Schema Extension**: Extend `AstroUserConfig` to include an optional `vite.preview` object with the same shape as Vite's `PreviewOptions` (`port`, `host`, `strictPort`, `https`, `open`, `allowedHosts`). Add TypeScript typings in `src/config/types.ts`.
* **PreviewConfig Class**: Introduce `src/core/preview/PreviewConfig.ts` that reads `astro.config.vite.preview`, validates it against Vite's schema using `vite`'s internal `validateConfig` helper, and provides defaults.
* **VitePluginAdapter Update**: Modify the `createViteServer` flow in `src/vite/pluginAdapter.ts` to merge `previewConfig` into the Vite dev server options when the `preview` command is invoked.
* **CLI Integration**: In `src/cli/commands/preview.ts`, instantiate `new PreviewConfig(astroConfig)` before calling `vite.preview`. Pass the resulting options to `vite.preview({ ... })`.
* **Testing**: Add unit tests in `tests/vite/preview-config.test.ts` that:
  - Set `allowedHosts: ["example.test"]` in a temporary Astro config.
  - Run `astro preview` in a child process.
  - Assert that the Vite preview server rejects requests from disallowed hosts and accepts the allowed one.
* **Documentation**: Update the configuration guide (`docs/configuration/preview.md`) with examples and TS code snippets.

4. Drawbacks
* **Increased Complexity**: Adding a new bridge layer introduces additional code paths that must be maintained across Vite major versions.
* **Potential Breakage**: Existing projects that relied on the implicit default behavior may experience preview failures if they previously accessed the server from a non‑localhost hostname without configuring `allowedHosts`.
* **Runtime Overhead**: Minimal, but the validation step adds a few milliseconds to preview startup.

5. Alternatives
* **No‑Op Pass‑Through**: Simply spread `astro.config.vite.preview` into Vite's preview call without a dedicated class. This reduces code but sacrifices validation and future extensibility.
* **Deprecate Preview**: Encourage users to run `vite preview` directly. This would offload responsibility to Vite but fragments the Astro workflow and breaks the unified CLI experience.
* **Environment Variable**: Allow `ASTRO_PREVIEW_ALLOWED_HOSTS` to override the setting. This adds flexibility but complicates configuration discovery and documentation.

6. Unresolved Questions
* How should Astro handle conflicting `host` values between the dev server and preview server when both are set?
* Should we expose a warning when `allowedHosts` is omitted but the user accesses the preview from a non‑localhost address?
* What is the migration path for existing projects that may have relied on the previous lax host checking?
* Will the new validation logic need to be updated for Vite 6's anticipated preview API changes?
