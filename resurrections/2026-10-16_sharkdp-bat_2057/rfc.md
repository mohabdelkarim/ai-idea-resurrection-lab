# RFC: output shell completion script by `bat --completion <shell>` command

1. Summary
Add a new command‑line flag `--completion <shell>` to the `bat` binary that prints a ready‑to‑use shell completion script for Bash, Zsh, Fish, or PowerShell. The flag is parsed via clap v4, maps to an internal `CompletionShell` enum, and invokes `clap::Command::generate_completion` to emit the script to stdout. The feature is optional behind a Cargo feature named `completion` to avoid impacting existing builds.

2. Motivation
`bat` is widely used in interactive shells, yet users must manually maintain completion scripts or rely on distribution packages that ship them separately. This leads to version drift: the shipped script may not reflect new subcommands or options. Modern clap (v4) provides a zero‑maintenance API to generate up‑to‑date completions directly from the argument definition. By exposing a `--completion` flag, we eliminate the need for separate script files in the repository, simplify packaging for all downstream distributions, and improve the end‑user experience. The change also aligns `bat` with other Rust CLI tools that already offer this ergonomics.

3. Detailed Design
- **CLI changes**: Extend the existing clap `Command` definition with an optional argument `--completion <SHELL>` where `<SHELL>` is one of `bash`, `zsh`, `fish`, `powershell`. The argument is hidden from normal help output unless the `completion` feature is enabled.
- **Enum**: Introduce `enum CompletionShell { Bash, Zsh, Fish, PowerShell }` with `FromStr` impl to map the string values.
- **Generation function**:
  ```rust
  fn generate_completion(shell: CompletionShell) {
      let mut cmd = build_cli(); // existing function returning clap::Command
      match shell {
          CompletionShell::Bash => cmd.generate_completion(clap_complete::Shell::Bash, &mut std::io::stdout()),
          CompletionShell::Zsh => cmd.generate_completion(clap_complete::Shell::Zsh, &mut std::io::stdout()),
          CompletionShell::Fish => cmd.generate_completion(clap_complete::Shell::Fish, &mut std::io::stdout()),
          CompletionShell::PowerShell => cmd.generate_completion(clap_complete::Shell::PowerShell, &mut std::io::stdout()),
      }
  }
  ```
- **Main entry point**: After parsing arguments, if `--completion` is present, call `generate_completion` and exit with code 0.
- **Cargo feature**: Add `completion = []` in `Cargo.toml`. The new code is compiled only when this feature is enabled, preserving the current binary size for users who do not need it.
- **Testing**: Add unit tests that invoke the binary with each shell argument and assert that the output contains known markers (e.g., `_bat` function for Bash, `complete -c bat` for Zsh). Use `assert!(output.contains("_bat"))` etc.
- **Documentation**: Update `README.md` and man page to include a section on generating completions, with examples for each shell and instructions for installing the output via standard locations (`/etc/bash_completion.d/`, `~/.zsh/completions/`, etc.).

4. Drawbacks
- Introducing a new optional dependency on `clap_complete` slightly increases compile time and binary size when the feature is enabled.
- Users who rely on the previously vendored static scripts must adjust their packaging pipelines to use the generated output instead of the old files.
- The flag adds another entry point that must be kept in sync with future CLI changes; however, because generation is driven directly from the clap definition, the risk is minimal.

5. Alternatives
- **Separate script files**: Keep static completion scripts in the repo and ship them via the package manager. This was the prior approach but caused version drift and extra maintenance.
- **External tool**: Instruct users to run `cargo install clap-completions` and generate scripts themselves. This offloads work but adds friction for non‑Rust users.
- **No completion support**: Accept the status quo; however, this would forgo the usability improvements and community expectations.

6. Unresolved Questions
- Should the `--completion` flag be hidden by default and only exposed when the `completion` feature is enabled, or always visible? The proposal leans toward always visible for discoverability, but we need consensus.
- Do we need to support older shells (e.g., `tcsh`) or only the four mainstream ones? Initial implementation targets the four most common shells.
- Should we provide a `--print-completion` alias for backward compatibility with any existing scripts that may have used a custom flag? No known usage, but we can discuss.
