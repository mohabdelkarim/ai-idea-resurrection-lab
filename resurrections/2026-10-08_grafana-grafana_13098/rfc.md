# RFC: [Feature] Row collapse status in URL

Summary
====
Add a first‑class URL parameter "rowCollapse" that persists the collapsed/expanded state of dashboard rows across shares and reloads. The implementation introduces a URLStateHandler in the dashboard package, extends DashboardState with a map[rowID]bool, and wires UI interactions to the new state sync API. Backward compatibility is maintained: when the parameter is missing the dashboard falls back to the default row state.

Motivation
====
Grafana users frequently share dashboard links via email, tickets, or chat. The visual context – especially which rows are expanded – is lost when the recipient opens the link, forcing them to manually re‑expand rows to locate panels. This friction reduces the usefulness of shared dashboards and leads to duplicated effort. In Grafana 8 and earlier the URL state serialization layer was monolithic and did not expose row collapse information, making a stable implementation impossible. Grafana 9 introduced the "state" package, a modular URL state manager with a clean API for custom keys, and the Go router now handles complex query strings efficiently. These changes eliminate the previous blockers, allowing us to persist row collapse state without inflating URL length beyond practical limits (the map is compact, encoding only rows that differ from the default).

Detailed Design
====
1. **Data Model**: Extend `DashboardState` (pkg/dashboard/state.go) with:
   ```go
   // RowCollapse maps a row UID to its collapsed flag. Only rows that differ from the default are stored.
   RowCollapse map[string]bool `json:"rowCollapse,omitempty"`
   ```
2. **URLStateHandler**: Add a new struct in `pkg/dashboard/urlstate.go`:
   ```go
   type URLStateHandler struct {
       encoder *state.Encoder
   }
   func NewURLStateHandler() *URLStateHandler { ... }
   func (h *URLStateHandler) Register() {
       state.RegisterKey("rowCollapse", h.encode, h.decode)
   }
   ```
   - `encode` serializes the `RowCollapse` map into a compact base‑64 string (e.g., `row1=1,row3=0`).
   - `decode` parses the string back into the map.
3. **UI Integration**:
   - The React component `Row` reads `dashboard.state.rowCollapse[row.uid]` on mount and sets its `collapsed` prop accordingly.
   - On toggle, the component dispatches `dashboard.actions.setRowCollapse(row.uid, collapsed)` which updates the state and calls `state.SyncToURL()`.
4. **Backward Compatibility**: If the query param is absent or malformed, the decoder returns an empty map, causing rows to use their configured default collapsed flag.
5. **Testing**:
   - Unit tests for encoder/decoder covering empty, full, and mixed maps.
   - End‑to‑end test: open a dashboard, collapse rows, copy URL, reload in a fresh browser, verify rows retain state.
6. **Documentation**: Update the "Sharing dashboards" section in the docs to describe the new `?rowCollapse=` parameter and provide examples.

Drawbacks
====
- **URL Length**: In dashboards with many rows (e.g., >100) the parameter could grow, but typical dashboards have <20 rows, keeping URLs well under 2 KB.
- **Cache Invalidation**: Some proxy caches treat query strings as separate resources; adding a new param may increase cache miss rates for shared links.
- **Complexity**: Introducing a new handler adds code paths that must be kept in sync with the existing state system, increasing maintenance surface.

Alternatives
====
1. **Local Storage**: Persist row collapse state in the browser's local storage. This would not survive link sharing, defeating the primary goal.
2. **Dashboard JSON**: Encode collapse state directly into the dashboard JSON and require users to save a copy. This is intrusive and forces a permanent change to the dashboard definition.
3. **Fragment Identifier**: Use `#rowCollapse=` instead of query parameters. Grafana already uses the query string for other state; mixing both would complicate the router logic.
All alternatives either lack shareability, introduce persistence issues, or conflict with existing URL handling.

Unresolved Questions
====
- **Row Identifier Stability**: Should we use the row UID (stable across edits) or the numeric index (which can change)? The proposal uses UID, but older dashboards may lack UIDs; a migration path is needed.
- **Security**: Do we need to validate the parameter size to prevent denial‑of‑service attacks via excessively long strings?
- **Feature Flag**: Should this be behind a feature flag for early adopters, or shipped default in the next minor release?
- **Interaction with Existing URL State**: How does the new key interact with the `state.SyncToURL` debounce logic under high‑frequency toggling?
