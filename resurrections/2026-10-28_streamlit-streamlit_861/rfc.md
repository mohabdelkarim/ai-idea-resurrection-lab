# RFC: Ability to write cookies

1. Summary
Streamlit will introduce first‑class cookie management through a new server‑side CookieManager and two experimental APIs: `st.experimental_set_cookie(name, value, **attrs)` and `st.experimental_get_cookie(name, default=None)`. The manager integrates with the existing SessionState system, persisting cookie data per user session and automatically emitting proper `Set-Cookie` headers on each HTTP response. A lightweight JavaScript shim will read `document.cookie` on the client, forward changes to the server via the existing RPC channel, and keep the server‑side view in sync. The feature will be gated behind the `enableCookieAPI` flag to preserve backward compatibility.

2. Motivation
Current Streamlit apps lack a reliable way to store authentication tokens or user preferences across page reloads without resorting to insecure work‑arounds (e.g., URL query parameters or hidden files). While SessionState keeps data only for the lifetime of a server process, cookies survive browser restarts and can be scoped with security attributes (Secure, HttpOnly, SameSite). Modern browsers now enforce consistent SameSite defaults, and Python's `http.cookies` module supports explicit attribute handling, removing the major security concerns that blocked earlier attempts. Providing a safe, declarative cookie API will enable developers to build authenticated dashboards, remember UI choices, and integrate with third‑party services that rely on cookies, all while staying within Streamlit's declarative programming model.

3. Detailed Design
**Server side**
- Add `streamlit.runtime.CookieManager` class. It maintains a dict of cookie objects per session ID, using the existing SessionState store as the persistence layer.
- On each request, the manager reads incoming `Cookie` headers, parses them with `http.cookies.SimpleCookie`, and populates `session_state['_cookies']`.
- `st.experimental_set_cookie(name, value, expires=None, max_age=None, path="/", domain=None, secure=True, httponly=True, samesite="Lax")` creates/updates an entry in the manager and marks the session as needing a header update.
- During the response phase, Streamlit's `Server.handle_response` will call `CookieManager.flush(session_id)`, which serialises each cookie to a `Set-Cookie` header using `http.cookies.Morsel` and attaches it to the HTTP response.

**Client side**
- A small JS bundle (loaded once per page) reads `document.cookie` after the page loads and sends a JSON payload `{name: value, ...}` via the existing `streamlit.setComponentValue` RPC.
- When the server calls `set_cookie`, the response includes the `Set-Cookie` header; the browser automatically stores it. The JS shim also listens for `streamlit.setCookie` messages (future extension) to update the client store without a full reload.

**Feature flag**
- Introduce `st.set_option('global.enableCookieAPI', False)`; default is False to avoid breaking existing deployments. Documentation will guide users to enable it.

**Testing**
- Unit tests for `CookieManager` parsing, attribute validation, and header generation.
- Integration tests with Selenium covering SameSite enforcement, Secure flag handling, and cross‑domain scenarios.

4. Drawbacks
- Adds a small amount of overhead to every request (parsing incoming cookies and potentially adding headers).
- Exposes a new attack surface; developers must understand security attributes to avoid XSS or CSRF risks.
- The experimental nature means API changes may be required before a stable release, potentially causing migration work for early adopters.

5. Alternatives
- **Query‑parameter persistence**: Already exists but leaks data in URLs and lacks security attributes.
- **LocalStorage wrapper**: Could be added via a custom component, but would not be sent automatically with HTTP requests, limiting use for server‑side authentication.
- **External authentication middleware**: Users could run Streamlit behind a reverse proxy that handles cookies, but this forces extra infrastructure and removes the convenience of a built‑in API.

6. Unresolved Questions
- How should the API handle cookie size limits (≈4KB) and large numbers of cookies? Should we enforce a hard limit or rely on browser behavior?
- Should we provide a `st.experimental_delete_cookie(name, path="/", domain=None)` helper now or defer to a later release?
- What is the best strategy for synchronising cookie deletions performed by client‑side JavaScript (e.g., user clears cookies) back to the server state?
- Will the feature be enabled by default in a future major version, and what migration path will be offered for apps that relied on the experimental flag?
