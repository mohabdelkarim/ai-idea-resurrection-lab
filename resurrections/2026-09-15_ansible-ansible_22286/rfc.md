# RFC: Feature Idea: add meta: end_role

Summary
---
Introduce a new meta directive `end_role` that allows a playbook author to terminate the execution of the current role immediately, mirroring the existing `meta: end_play` behavior. The directive will be implemented as a MetaPlugin (`end_role.py`) that sets a flag in the task result. The strategy layer will detect the flag and raise a `RoleTerminator` exception, causing the executor to skip any remaining tasks in the role while preserving the surrounding play context. This feature requires no core code modifications beyond adding a hook in the existing strategy API, which is now extensible via the collection architecture introduced in Ansible 2.12.

Motivation
---
Roles are a primary mechanism for reusing logic across playbooks. Complex roles often contain conditional branches where, under certain circumstances, the remaining tasks become irrelevant or even harmful (e.g., when a prerequisite check fails). Currently the only built‑in way to abort execution is `meta: end_play`, which ends the entire play, not just the role. Users resort to work‑arounds such as setting `when: false` on every subsequent task or using `include_role` with `apply` and `failed_when`. These approaches are verbose, error‑prone, and obscure intent. Providing an `end_role` meta directive gives a clear, declarative way to stop role processing, improves readability, and aligns role control flow with play‑level control flow.

Detailed Design
---
1. **Meta Plugin**: Create `ansible/plugins/meta/end_role.py` extending `MetaBase`. The plugin implements `run(self, task_vars)` and returns a result dict containing `changed: false` and a custom flag `end_role: true`.
2. **Strategy Hook**: Extend the `BaseStrategy` class (already plugin‑based) with a new method `handle_meta_end_role(self, result)`. The existing `run_task` loop will invoke this hook after each task result is processed. If `result.get('end_role')` is true, the hook raises a new exception `RoleTerminator`.
3. **Exception Propagation**: Define `RoleTerminator` in `ansible/executor/task_queue_manager.py`. The `TaskQueueManager` catches this exception, marks the current role as completed, and continues with the next role or task in the play.
4. **YAML Schema**: Add `end_role` to the meta schema (`lib/ansible/config/schema/meta.json`) using the existing validation framework, ensuring users receive helpful error messages for misspellings.
5. **Collection Registration**: The plugin is discoverable via the collection entry point `ansible.meta_plugins`. No core changes are required; the plugin is loaded like any other meta plugin.
6. **Testing**: Add unit tests in `test/units/plugins/meta/test_end_role.py` using `ansible-test`. Tests will mock a role with several tasks, insert `meta: end_role` mid‑stream, and assert that subsequent tasks are not executed while the play continues.
7. **Documentation**: Update the User Guide (`docs/user_guide/playbooks_roles.rst`) with a section "Early Role Termination" and provide examples.

Drawbacks
---
* **Complexity in Debugging**: Early termination may hide failures in tasks that are skipped, making troubleshooting harder if users are unaware of the directive.
* **Potential Misuse**: Overuse could lead to fragmented role logic, encouraging developers to split roles unnecessarily.
* **Performance Overhead**: Introducing an extra check after each task adds minimal runtime cost, but in very large playbooks the cumulative effect is measurable.

Alternatives
---
1. **Conditional Includes**: Use `include_role` with `when` clauses to conditionally load the remainder of a role. This avoids engine changes but requires restructuring the role into multiple sub‑roles.
2. **Task Skipping via `when: false`**: Manually set `when: false` on all remaining tasks after a condition. This is verbose and brittle.
3. **Custom Callback Plugin**: Write a callback that aborts role execution based on a variable. This works but lacks the declarative syntax and schema validation of a meta directive.

Unresolved Questions
---
* Should `end_role` propagate a failure status (i.e., mark the role as failed) or always be considered successful? The initial design treats it as a neutral termination, but use cases may require a failure flag.
* How should `end_role` interact with `block/rescue/always` constructs inside a role? Should the rescue block still execute?
* Will future strategy plugins (e.g., `free`, `host_pinned`) need additional adaptations to respect the new exception?
* Should a complementary `meta: skip_role` be introduced to skip the role without executing any tasks at all?
