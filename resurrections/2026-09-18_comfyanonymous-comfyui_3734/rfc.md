# RFC: [Feature] Support for SD3 ControlNet

Summary
---
Add a new ControlNetNode to ComfyUI that wraps the Diffusers SD3ControlNetPipeline. The node will expose sockets for an SD3 base model, conditioning images, and strength parameters, and will allow selection of different ControlNet types (Canny, Pose, Tile, Inpainting) via UI widgets. This enables native SD3 ControlNet workflows without custom scripting.

Motivation
---
When the original issue was filed, ComfyUI lacked SD3 model support and Diffusers had no stable SD3 ControlNet API, making implementation impractical. Since then, Diffusers 0.23 (2025) introduced a stable SD3ControlNetPipeline, ComfyUI 2.1 added native SD3 loading, and PyTorch 2.2 provides optimized kernels, dramatically lowering the engineering effort and runtime cost. Users now demand SD3‑based ControlNet for higher‑quality generation, and the ecosystem (HuggingFace Hub) supplies pre‑converted ControlNet weights with metadata. Providing first‑class node support will keep ComfyUI competitive and reduce fragmentation of ad‑hoc scripts.

Detailed Design
---
1. **Node Class**: Create `SD3ControlNetNode` inheriting from `ComfyNode`. Constructor registers input sockets:
   - `sd3_model` (BaseModel)
   - `conditioning_image` (Image)
   - `strength` (Float, default 1.0)
   - `controlnet_type` (Enum: CANNY, POSE, TILE, INPAINTING)
   - `controlnet_weights` (String, HF repo identifier)
   Output socket: `latent` (Latent).
2. **Pipeline Instantiation**:
   ```python
   from diffusers import StableDiffusion3ControlNetPipeline, AutoencoderKL, UNet2DConditionModel
   pipeline = StableDiffusion3ControlNetPipeline.from_pretrained(
       sd3_model_path,
       controlnet=controlnet_path,
       torch_dtype=torch.float16,
       variant="fp16",
   )
   pipeline.scheduler = get_scheduler(selected_scheduler)
   ```
   The node caches the pipeline per unique weight combo to avoid re‑loading.
3. **UI Widgets**:
   - Dropdown for `controlnet_type` that maps to known HF repos.
   - Text field / browse button for `controlnet_weights`.
   - Slider for `strength` (0.0‑2.0).
4. **Execution Flow**:
   - Validate that `sd3_model` and `controlnet_weights` are present; log errors via `comfyui.logger`.
   - Preprocess `conditioning_image` (resize to model resolution, normalize).
   - Call `pipeline(prompt, image=cond, controlnet_conditioning_scale=strength, num_inference_steps=steps, ...)`.
   - Return the generated latent to downstream nodes.
5. **Error Handling**:
   - Catch `OSError` for missing weights, raise a UI‑visible warning.
   - If GPU OOM occurs, fallback to CPU with a logged notice.
6. **Testing**:
   - Unit tests mock `StableDiffusion3ControlNetPipeline` to assert that node forwards parameters correctly.
   - Integration test runs a minimal 8‑step generation on a CI GPU instance.

Drawbacks
---
* **Increased Memory Footprint**: Loading both an SD3 UNet and a ControlNet model roughly doubles VRAM usage, potentially exceeding the limits of older consumer GPUs.
* **Complexity in Scheduler Compatibility**: Not all schedulers are verified with ControlNet; mismatches could produce artifacts, requiring additional validation.
* **Maintenance Overhead**: The node must track Diffusers API changes; a breaking change in future Diffusers releases would necessitate updates.

Alternatives
---
1. **External Script Wrapper**: Keep the current approach of invoking a Python script that builds the Diffusers pipeline outside the node graph. This avoids UI changes but forces users to manage subprocesses and data passing manually.
2. **Generic ControlNet Wrapper**: Implement a single generic ControlNet node that works for SD1‑SD2 and SD3 by abstracting the pipeline selection. This reduces duplication but adds runtime branching and may hide SD3‑specific optimizations.
3. **Deferred Implementation**: Wait for a community‑maintained plugin that adds SD3 ControlNet support. This postpones work but leaves the core repository without first‑class support.

Unresolved Questions
---
* Which scheduler(s) should be enabled by default for SD3 ControlNet? Preliminary testing favors `EulerDiscreteScheduler`, but `DPMSolverMultistepScheduler` may offer better speed.
* How should the node expose advanced ControlNet options such as `guess_mode` or `batch_size` without cluttering the UI?
* Is there a need for a caching policy (LRU vs. explicit unload) to manage VRAM on machines with multiple ControlNet nodes in a single graph?
* Should the node support multi‑controlnet chaining (multiple conditioning images) now, or be limited to a single instance per node?
