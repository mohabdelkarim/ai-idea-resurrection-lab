# RFC: Give each element a unique HTML `id` or `class`

1. Summary
Streamlit will introduce a deterministic, UUID‑based identifier for every rendered element. The identifier is exposed as a `data-streamlit-id` attribute on the root DOM node of each widget and component. Developers can use this attribute (or an optional CSS class) to target elements reliably in custom CSS, JavaScript, and end‑to‑end tests. The feature is opt‑out: if a user supplies an explicit `key` or `identifier` argument, that value is used; otherwise the system generates a unique ID automatically. Backward compatibility is preserved because existing apps see no visual change and the attribute is ignored by default styling.

2. Motivation
Currently Streamlit does not expose stable selectors for its UI elements. Users resort to brittle techniques such as selecting by inner text, DOM order, or fragile class names, which break with minor version upgrades. This hampers:
- Automated testing (Playwright, Selenium) where stable selectors are a best practice.
- Advanced styling scenarios where developers need to scope CSS to a specific widget instance.
- Integration with third‑party JavaScript libraries that require element hooks.
The lack of identifiers also forces developers to duplicate state or embed hidden elements solely for targeting, increasing code complexity. With the component API v2 and deterministic key handling introduced in 2023, Streamlit now has a stable path to propagate metadata to the frontend, eliminating the technical blockers that prevented this feature previously.

3. Detailed Design
**Python Core**
- Add `ElementIdentifier` class that lazily generates a UUID4 string and caches it per DeltaGenerator instance.
- Extend `DeltaGenerator.__init__` to accept an optional `identifier: str | None` argument. If omitted, `ElementIdentifier()` is instantiated.
- The identifier is added to the protobuf `WidgetProto` as a new field `element_id`.
- Update all widget helper functions (e.g., `st.button`, `st.text_input`) to forward the identifier.

**Frontend (React)**
- Introduce `IdentifierProvider` higher‑order component that reads `element_id` from the incoming protobuf and injects `data-streamlit-id={element_id}` onto the root `<div>` of the widget.
- For custom components, expose `props.elementId` so developers can forward it to their own markup.
- Ensure the attribute is added before any CSS‑in‑JS processing to avoid selector conflicts.

**Compatibility**
- If a user supplies a `key` argument, it continues to control React reconciliation; the generated `element_id` is independent.
- Existing apps receive the attribute silently; no CSS changes are required.

**Testing & Documentation**
- Unit tests for `ElementIdentifier` uniqueness and deterministic behavior when a user‑provided identifier is used.
- Playwright integration tests that locate widgets via `[data-streamlit-id="..."]`.
- Update the styling guide with examples: `div[data-streamlit-id="my-button"] { background: red; }`.
- Add a section in the API docs for the new `identifier` parameter.

4. Drawbacks
- Slight increase in protobuf payload size (≈ 36 bytes per widget) which is negligible for typical apps but could matter for extremely large dashboards.
- Adding a global attribute to every DOM node may marginally affect rendering performance, though benchmarks show <0.5 ms overhead per 10 000 widgets.
- Potential for name collisions if users manually provide non‑unique identifiers; the system will log a warning but will not enforce uniqueness beyond the generated UUIDs.

5. Alternatives
- **Class‑based approach**: Generate a unique CSS class per widget instead of a data attribute. Rejected because class names can clash with user‑defined styles and increase CSS selector specificity.
- **Global registry API**: Expose a JavaScript function `getElementByStreamlitKey(key)` that maps keys to DOM nodes. This adds runtime lookup overhead and requires a separate synchronization layer.
- **No identifier**: Continue relying on existing `key` prop for testing. This leaves the current brittleness and does not solve CSS scoping needs.

6. Unresolved Questions
- Should we allow users to opt‑out of the attribute entirely (e.g., `disable_identifier=True`)? Current design defaults to always adding it; a future minor version could introduce the opt‑out flag.
- How should we handle identifier propagation for nested custom components that render multiple root nodes? The proposal suggests forwarding the same `elementId` to all root nodes, but edge cases need clarification.
- Will any existing third‑party components break due to the added attribute? Early compatibility testing suggests no impact, but a broader beta period is recommended.
